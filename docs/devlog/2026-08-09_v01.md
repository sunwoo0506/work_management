## 겪은 이슈와 처리

### 1. git 저장소가 통째로 망가져 있었다

**증상.** `jeus` 폴더에 `.git` 디렉터리가 있는데 `git status`를 치면 `fatal: not a git repository`가 떴다.

**원인.** `.git`이 OneDrive의 **클라우드 자리표시자(placeholder)**로만 남아 있었다. 폴더 이름은 있는데 안이 텅 비어 있는 상태다. OneDrive가 "안 쓰는 파일은 클라우드에만 두고 로컬에서 지우는" 동작을 하는데, 그게 `.git` 내부 파일에까지 적용된 것이다. `(Get-Item .git).Attributes`를 찍어보니 `ReparsePoint`가 붙어 있었다.

**처리.** 안에 아무것도 없어서 잃을 게 없었다. 지우고 새로 `git init`했다.

**주의.** OneDrive 폴더 안에서 git을 쓰면 이런 일이 또 생길 수 있다. 저장소를 OneDrive 밖으로 옮기는 게 근본 해결책이다. 지금은 그대로 두되, 이상하면 이 항목을 먼저 의심할 것.

### 2. 사외 반출 금지 문서가 GitHub에 올라갈 뻔했다

**증상.** 처음엔 `jeus/` 폴더 전체를 저장소로 잡으려 했다.

**문제.** `jeus/` 안에 `제우스_3대사업축_사업이해자료_vfin.docx`가 있는데, 표지에 **「내부 자료 · 사외 반출 금지」**라고 명시돼 있다. GitHub는 private이라도 외부 서버다. `.gitignore`로 막을 수도 있지만, 규칙 한 줄 실수하면 그대로 올라간다.

**처리.** 저장소 루트를 `jeus/Work_Management/`로 한 단계 내렸다. 그러면 사업이해자료·PRD·`management.db`가 **애초에 git의 관할 밖**이라 실수의 여지 자체가 없어진다. 첫 커밋 전에 `git ls-files`로 민감 파일이 없는 것도 확인했다.

**왜 이 방법인가.** `.gitignore`는 "올리지 말라고 부탁하는 것"이고, 저장소 밖에 두는 건 "올릴 수가 없는 것"이다. 되돌릴 수 없는 사고에는 후자를 쓴다.

### 3. 테스트가 시간대에 따라 깨지는 상태였다 — 가장 중요한 이슈

**증상.** 당장은 아무 문제가 없었다. 테스트 16개가 전부 통과했다.

**문제.** D-day 계산 테스트의 기준 시각이 이렇게 돼 있었다.

```ts
const TODAY = new Date('2026-08-11T09:00:00+09:00')
```

이건 **절대 시각**을 고정한다. UTC로는 `2026-08-11T00:00:00Z`다. 그런데 구현은 `daysUntil`이 **로컬 달력일**을 비교한다. 이 둘은 UTC 오프셋이 0 이상인 지역에서만 일치한다.

한국(+9)이나 독일(+2)에서는 맞는다. 그런데 뉴욕(−4)에서 돌리면 그 순간의 로컬 날짜가 **8월 10일**이 된다. "오늘"이 하루 밀리면서 `오늘이면 0`, `오늘 마감은 임박`, `기한이 지나면 지연`, `8일 뒤는 정상` 네 개가 한꺼번에 깨진다.

즉 **출장을 가거나, 노트북 시간대가 다르게 잡혀 있으면 빨간 화면을 보게 된다.**

**하마터면 놓칠 뻔한 부분.** 처음엔 `TZ=America/New_York npm test`로 확인해봤고 "통과했다"는 결과가 나왔다. 그런데 이 결과가 **거짓**이었다. **Windows의 Node는 `TZ` 환경변수를 무시한다.** `Intl.DateTimeFormat().resolvedOptions().timeZone`을 찍어보니 세 번 다 `Asia/Seoul`이었다. 검증 방법 자체를 검증하지 않았으면 "문제 없음"으로 결론 낼 뻔했다.

**처리.** 구현은 그대로 두고 **픽스처만** 로컬 벽시계 리터럴로 바꿨다.

```ts
// 로컬 벽시계 기준. ISO 문자열(절대 시각)로 바꾸면 UTC 오프셋이 음수인 지역에서 하루가 밀려 깨진다.
const TODAY = new Date(2026, 7, 11, 9, 0)
```

`new Date(2026, 7, 11, 9, 0)`은 "어느 시간대에서든 8월 11일 오전 9시(현지)"를 뜻한다. 그래서 `atMidnight(TODAY)`와 `parseDate('2026-08-11')`이 항상 같은 로컬 자정으로 떨어진다. **운이 좋아서 통과하는 게 아니라 구조적으로 통과한다.**

**왜 구현이 아니라 테스트를 고쳤나.** "로컬 달력일로 비교한다"는 게 이 도메인의 규칙이 맞기 때문이다. 사용자가 보는 "오늘"은 UTC가 아니라 자기 시계다. 구현이 옳고 픽스처가 틀렸다.

**같은 문제가 계획서의 Task 7에도 있어서** 미리 고쳤다. 안 고쳤으면 정렬 테스트가 같은 결함을 그대로 물려받았을 것이다.

### 4. 구현 계획서 자체에 오류가 있었다

**증상.** 계획서에는 D-day 테스트가 15개라고 적혀 있는데 실제로는 16개였다.

**원인.** 계획을 쓸 때 손으로 센 것이 틀렸다. 5 + 7 + 4 = 16인데 15로 적었다.

**파장.** 뒤따르는 태스크가 전부 누적 개수를 쓰기 때문에 21 / 27 / 34가 전부 하나씩 밀려 있었다. 그대로 뒀으면 "22개 나왔는데 계획서는 21개라니, 뭔가 잘못됐나?" 하고 헛수고할 뻔했다.

**처리.** 16 / 22 / 28 / 35로 바로잡고 커밋했다(`9c6e847`).

**교훈.** 계획서의 숫자도 검증 대상이다. 실제 실행 결과와 다르면 계획서를 고친다.

### 5. 스택 버전이 예상보다 훨씬 최신이었다

**증상.** `npm create vite@latest`가 깐 것들: Vite **8.2**, TypeScript **6.0**, React **19.2**, vitest **4.1**, jsdom **29**, Tailwind **4.3**.

**왜 신경 쓰나.** 계획을 쓸 때 상정한 것보다 한 세대 앞선 버전들이다. Tailwind는 v3와 v4의 설정 방식이 완전히 다르고(v4는 `tailwind.config.js`가 없다), 스캐폴드도 ESLint 대신 **oxlint**를 깐다.

**처리.** 전부 빌드·테스트가 통과하는 것을 확인하고 그대로 갔다. 다만 앞으로 뭔가 이상하면 **버전 차이를 먼저 의심**하도록 `CLAUDE.md`에 적어뒀다.

### 6. 테스트 타입이 안 잡히는 문제

**증상.** 테스트 파일에서 `describe`, `it`, `expect`가 `TS2593` 오류로 잡혔다.

**원인.** Vite 스캐폴드의 `tsconfig.app.json`이 `types`를 `["vite/client"]`로 고정해두는데, vitest 설정에서 `globals: true`를 켰으니 그에 맞는 타입 항목이 없었던 것이다.

**처리.** `types`에 `"vitest/globals"`를 추가했다. 이걸 안 했으면 도메인 태스크 4개의 테스트 파일이 전부 `npm run build`를 깨뜨렸을 것이다.

### 7. Bash 툴에서 PowerShell 문법을 써서 커밋 메시지가 깨졌다 (두 번)

**증상.** 커밋 메시지에 `@` 문자가 그대로 남았다.

**원인.** Windows 환경이라 무심코 PowerShell here-string(`@'...'@`)을 Bash 툴에서 썼다. Bash는 `@`를 특별 취급하지 않아서 그대로 문자열에 들어간다.

**처리.** 둘 다 `git commit --amend`로 고쳤다. push 전이라 영향은 없었다.

**재발 방지.** `CLAUDE.md`에 "Bash 툴에서 here-string 금지, heredoc(`<<'EOF'`)을 쓸 것"으로 적었다.

## 결정한 것

### 기술 스택을 두 번 바꿨다

처음엔 **Streamlit**으로 시작했다(v1·v2·v3까지 만들었다). 그런데 하루 종일 켜두고 빠르게 입력하는 도구인데 Streamlit은 클릭할 때마다 화면 전체가 다시 그려진다. 칸반 드래그앤드롭도 안 되고, 폰에서 열 수도 없다.

**React + 로컬 FastAPI**를 거쳐 최종적으로 **React + Supabase**로 갔다. 결정적인 이유는 **"PC가 꺼져 있을 때도 써야 하는가"**였다. 로컬 백엔드는 그 PC가 서버라서 꺼지면 서비스도 꺼진다. 노트북·폰에서 항상 쓰려면 클라우드가 필요하다.

**대가:** 업무 데이터가 외부 서버에 저장된다. 회사가 이미 이카운트·위하고 같은 외부 SaaS를 쓰고 있어서 그 자체가 금기는 아니지만, **회생·인사 회의는 결이 다르다**. 그래서 민감 회의는 전사문을 Supabase에 저장하지 않고 로컬에만 두기로 했다(설계서 §4.3).

### 음성 인식은 로컬에서 돌린다

폰 녹음을 올려 회의록을 자동 생성하는 기능이 있는데, 음성을 클라우드 STT로 보내면 회의 내용이 통째로 외부에 나간다.

PC 사양을 확인해보니 **RTX 3060 Laptop 6GB**가 있었다. Whisper `large-v3`가 VRAM 4.7GB를 쓰니 들어간다. 1시간 회의가 **2~5분**이면 전사된다. 클라우드를 쓸 이유였던 속도 이점이 거의 사라진다.

그래서 로컬 Whisper로 정했다. 비용 0원, 음성이 PC를 벗어나지 않는다.

### 도메인 로직을 Supabase에서 분리했다

`src/domain/`은 Supabase도 React도 import하지 않는다. 날짜 계산·정렬·집계·매핑이 여기 모여 있다.

**왜.** 설계 단계에서 "날짜 경계 로직이 틀리기 쉽다"고 짚었는데, DB에 붙어 있으면 테스트가 느리고 불안정해진다. 분리해두니 35개 테스트가 **1.7초**에 돈다. 그리고 실제로 이 구조 덕분에 위 3번 결함을 잡았다.

### 인박스를 1단계로 앞당겼다

원래 2단계였는데, 하루 종일 쓰는 진입점이라 「오늘」 화면보다 먼저 있어야 쓸모가 있다고 판단했다.

다만 1단계 인박스는 **직접 던져둔 메모만** 받는다. 회의록·전화메모에서 흘러드는 경로는 3·4단계에서 붙는다.
