## 0. 이 문서를 읽기 전에 — 지금의 상황

### 0.1 어떤 자리에서 시작하는가

제우스는 세 개의 사업축(농자재·데이터 / 시공·인력·과원관리 / 농지·유통연결)으로 운영되는 회사다. 경영지원부장이 새로 부임해 인수인계를 받는 중이고, 대표 지시사항이 실제 업무로 전개되기 시작하는 시점이다.

지금 회사에는 두 가지가 동시에 없다.

1. **숫자가 정리되지 않는다.** 품목 분류·판매가·단위 환산·재고 실사·축별 손익이 체계적으로 관리되지 않아, 대표는 무슨 문제가 있는지 한눈에 보지 못한다.
2. **일하는 방식이 기록되지 않는다.** 부가세 신고든 월 마감이든 매번 하지만 어떻게 하는지가 어디에도 안 남는다. 사람이 바뀌면 처음부터 다시다.

이 두 문제는 성격이 완전히 다르다. **그래서 도구를 두 개 만든다.**

### 0.2 두 개의 도구가 동시에 만들어지고 있다

| | **경영관리서비스** | **업무관리툴** (이 저장소) |
|---|---|---|
| 저장소 | `Desktop/jeus/` | `Desktop/WorkManagement/` |
| 푸는 문제 | 숫자가 정리되지 않는다 | 일하는 방식이 기록되지 않는다 |
| 보는 사람 | 대표 · 임원 · 관련 업무 담당자 | 경영지원부장 1인 + AI |
| 문서 | `PRD_경영관리서비스.md` | **이 문서** |

**두 저장소는 완전히 분리되어 있고, 파일을 서로 옮기지 않는다.** 다만 §2에서 정의하는 계약으로 데이터를 주고받는다.

### 0.3 왜 「AI 업무학습」인가

향후 AI 업무비서를 두는 것이 목표다. 대표나 담당자가 경영관리서비스에서 실시간으로 묻고, AI가 답하고 보고서를 쓰고, 주기적인 행정 신고 문서의 초안을 만들고, 일정에 맞춰 미리 준비하고, 자금 상황을 파악해 경고하는 그림이다.

그런데 **AI를 붙인다고 저절로 되는 일이 아니다.** AI가 부가세 신고를 대신하려면 그 일을 어떻게 하는지가 데이터로 있어야 하는데, 지금은 어디에도 없다. 지금부터 쌓지 않으면 2년 뒤에도 없다. 그때 가서 "작년 것부터 절차로 정리해 주세요"는 불가능하다 — 뭘 어떻게 했는지 아무도 기억하지 못하기 때문이다.

**이 저장소가 만드는 것은 AI가 일하고 배우는 작업대다.** 그 위에서 AI는 두 가지를 한다 — 지금은 **내 업무를 돕고**(문서 초안·절차 추출·예외 설명, §5.10), 데이터가 쌓이면 **경영관리서비스에서 대표의 질문에 답한다**. 뒤쪽 창구는 그쪽 저장소가 만든다.

### 0.4 이 문서의 범위

이 문서는 **업무관리툴이 무엇을 왜 만드는가**의 원본이다. 구현 순서는 `docs/plans/`, 두 툴 사이의 인터페이스 상세는 별도 「연동 계약서」, 개발 중의 판단 경위는 `docs/retro/`에 있다.

구현 중 이 설계와 다른 판단이 필요하면 **이 문서를 먼저 고치고, 그 경위를 회고에 남긴다.**

## 1. 무엇을 만드는가

> **업무관리툴은 경영지원부장과 AI가 함께 일하는 작업장이며, 그 일하는 방식이 데이터로 남아 나중에 AI가 넘겨받을 수 있게 하는 곳이다.**
> **밖으로 나가는 것은 내가 「공유」를 누른 것뿐이다.**

### 1.1 해결하려는 문제 — 두 가지다

**문제 1. 하루가 이어지지 않는다**

인수인계로 시작해 대표 지시사항이 실제 업무로 전개되는데, 그 사이를 이어줄 도구가 없다. 어제 어디서 멈췄는지, 오늘 뭘 해야 하는지, 누구에게 뭘 요청했고 회신을 받았는지가 흩어진다.

**문제 2. 업무 지식이 사람 머릿속에만 있다**

부가세 신고, 월 마감, 재고 실사 같은 일을 매번 하지만 **어떻게 하는지가 어디에도 안 남는다.**

흔한 할일 앱을 1년 써도 남는 것은 이것뿐이다:

> 「부가세 신고」라는 제목의 업무가 8월 25일에 완료됨

이 기록으로는 누구도 — 사람이든 AI든 — 그 일을 넘겨받을 수 없다.

### 1.2 남겨야 하는 세 층

| 층 | 무엇을 남기나 | 예 |
|---|---|---|
| **무엇을 했나** | 제목·상태·기한·진행률 | "부가세 신고, 8월 25일 완료" |
| **어떻게 했나** | 어떤 자료를 어디서 받아, 무슨 순서로, 무엇을 보고 판단했는가 | "이카운트에서 매출·매입 추출 → 위하고 원장과 대사 → 차이 10만원 초과 시 원인 규명 → 세무대리인 확인 → 신고" |
| **왜 그렇게 했나** | 절차대로 안 됐을 때의 판단 근거 | "이번엔 세무대리인 확인을 건너뛰었다. 직전 분기와 항목이 동일해서" |

**아래 두 층을 만드는 것이 이 제품의 핵심이다.** 위 한 층만 있는 도구는 이미 많다.

### 1.3 비목표

- **숫자 집계를 하지 않는다.** 축별 손익·재고·현금 집계는 경영관리서비스의 몫이다. 이 서비스는 "그 숫자를 만드는 일"만 관리한다.
- **이카운트·위하고와 연동하지 않는다.** 외부 시스템 연동은 경영관리서비스가 담당한다(그쪽 PRD §8).
- **대표·담당자용 대화형 질의응답 인터페이스를 만들지 않는다.** "지금 재고 어때?"에 답하는 창구는 경영관리서비스다.
  - **이 툴에도 AI는 들어간다**(§5.10). 다만 성격이 다르다 — **내 업무를 돕는 작업 도우미**이지, 남의 질문에 답하는 비서가 아니다.
- **다른 사람과 협업하지 않는다.** 단독 사용이 전제다. 다만 **내가 고른 이슈만** 경영관리서비스로 발행한다(§2.3).
- 개인 생활 영역(습관·재정·여행 등)을 다루지 않는다.

## 2. 두 툴의 경계 — 이 설계서에서 가장 중요한 부분

### 2.1 경계를 먼저 못 박는 이유

경영관리서비스 PRD **§5.0.1 「업무관리 탭」**이 업무 등록·칸반·마일스톤·체크리스트·반복업무·지연관리를 전부 P0로 명세하고 있고, 데이터 모델 §7.1에 `WorkItem`·`Milestone`·`ChecklistItem`이 있다. **이 저장소가 만들려는 것과 정면으로 겹친다.**

같은 업무가 두 DB에 각각 존재하면

1. 어느 쪽이 진짜인지 매일 어긋나고 — "칸반에서 옮겼는데 왜 저기선 안 옮겨졌지",
2. **AI가 오염된 데이터를 학습한다.** 학습 툴로서는 치명적이다.

또한 경영관리 PRD는 §1.4 비목표에서 *"구매·영업·현장 담당자가 매일 접속해 업무를 처리하는 부서별 운영시스템"*과 *"현업 부서의 프로젝트 관리 도구 대체"*를 하지 않는다고 선언해 놓고, §5.0.3에서 정확히 그것을 명세하고 있다. **업무 실행 기능을 이 저장소로 옮기면 그 모순도 함께 해소된다.**

### 2.2 책임 분할

| | **업무관리툴** (이 저장소) | **경영관리서비스** |
|---|---|---|
| 한 줄 | 내 작업장 · AI의 학습장 | 회사의 데이터 창고 · 보고와 대화의 장 |
| 사용자 | 경영지원부장 1인 + AI | 대표 · 임원 · 관련 업무 담당자 |
| 소유하는 것 | 업무 · **절차** · **실행이력** · **예외사례** · 업무일지 · 인박스 · 회의록 · 지시사항 | 숫자(손익·재고·현금) · 이슈 · 보고서 · 대표 알림 · 커뮤니케이션 |
| 기본 공개 | **비공개** — 자동으로 나가는 것이 없다 | 관련자에게 공개 |
| 숫자 | 만지지 않는다 | 여기가 원본 |
| AI와의 관계 | AI가 여기서 **일하고 배운다** | AI를 **호출해 묻는다** |

### 2.3 두 툴 사이의 계약

```
        업무관리툴                              경영관리서비스
   ┌──────────────────┐                  ┌──────────────────┐
   │  업무 · 절차     │  ── 이슈 발행 ──▶│   이슈 관리대장   │
   │  실행이력        │   (내가 고른 것만)│   (ISS-002 대응)  │
   │  일지 · 회의록   │                  │                  │
   │                  │◀── 지시 · 회신 ──│   대표 지시       │
   │  📥 인박스       │                  │   담당부서 회신   │
   └──────────────────┘                  └──────────────────┘
         비공개                                 공개
```

**나가는 것 — 내가 「이슈로 공유」를 누를 때만**

| 나가는 필드 | 나가지 않는 것 |
|---|---|
| 제목 · 핵심 내용 · 사실/추정 구분 · 재무영향 · 요청 결정 · 근거 | 업무 제목 · 진행률 · 체크리스트 · 일지 · **절차** · **실행이력** · 소요시간 |

경영관리 PRD의 **ISS-002(수동 이슈 등록)** 자리에 그대로 꽂힌다. 그쪽 PRD를 고치지 않아도 붙는다.

**들어오는 것 — 두 갈래**

| 유입 | 처리 |
|---|---|
| **대표 지시(확정건)** | 📥 인박스를 **건너뛰고 바로 업무로 등록.** 중요도 `P0`, 출처 `대표지시` |
| 발행한 이슈의 회신 · 배정된 이슈 | 📥 **인박스로.** 내가 보고 업무로 승격 |

대표 지시가 인박스를 건너뛰는 이유 — 이미 확정된 지시라 분류할 필요가 없고, 인박스에 섞이면 우선순위가 묻힌다.

**주간·월간 보고서는 밖으로 나가지 않는다.** 내가 내 일을 모니터링하고 연말 성과평가에 쓰는 **내부 자료**다(§5.5).

### 2.4 경영관리서비스에 요청할 사항

경영관리서비스 PRD에서 아래를 제거하고, 필요하면 이 저장소를 읽는 뷰로 대체한다.

- §5.0.1 「업무관리 탭 — 공통」의 업무 실행 기능 (WRK-001 ~ WRK-010)
- §5.0.2 · §5.0.3의 업무탭 실행 기능
- §7.1 데이터 모델의 `WorkItem` · `Milestone` · `ChecklistItem`

**시점이 중요하다.** 경영관리서비스가 재정리 중인 지금이 경계를 옮길 수 있는 시점이고, 그쪽 설계가 굳으면 중복이 확정된다. → §14 OQ-01

## 4. 메뉴 구조

사이드바 6탭. **하루 종일 켜두는 도구라 사이드바가 짧을수록 시선이 덜 분산된다.**

```
[업체 셀렉터]        ← 업체가 2개 이상일 때만 표시

빠른 입력
  ＋ 새 업무   ＋ 회의록   ＋ 전화메모

메뉴
  📌 오늘
  📋 업무          목록 / 칸반. 출처로 구분
  ⚙️ 절차          절차 라이브러리 · 실행이력 · ⚠️예외 확인함
  🗓 계획          주간 · 월간 · 마일스톤
  ✏️ 기록          업무일지 · 회의록 · 전화메모 · 리포트
  📖 기준          지시사항 · 인수인계 · 연락처 · 업체 · 설정

오늘 한눈에
  할 일 n · 지연 n · 회신 대기 n · 인박스 n · ⚠️예외 n
```

- **「이슈로 공유」는 탭이 아니라 업무 상세 화면 안의 버튼이다.** 일하다가 누르는 것이지, 발행하러 가는 곳이 아니다.
- **리포트를 「기록」에 넣은 이유** — 되돌아보는 것끼리 모여야 연말에 한 곳만 열면 된다.
- **「예외 확인함」을 인박스에 합치지 않은 이유** — 인박스는 *"업무가 될 것"*, 예외 확인함은 *"절차를 고칠 것"* 이라 처리 방식이 다르다.

### 4.1 「오늘」 화면

**블록 순서가 곧 하루의 순서다.**

| 블록 | 내용 |
|---|---|
| **어제 이야기** | 전날 일지의 「이슈·막힌 것」, 전날 완료한 업무, 일지에서 업무로 올리지 않은 메모 |
| **오늘 할 일** | 체크 목록. 어제 일지의 「내일 할 일」 중 체크한 것 + 오늘 기한 도래 업무 + 오늘 하기로 찍은 업무 |
| **진행 중 업무** | 지시사항 단위 묶음. 타임라인 뷰(기본) / 목록 뷰 전환. 시작일·마감일·D-day·진행률·업무 건수 |
| **인박스** | 맨 하단. 분류 전 메모 |
| 우측 — **이번 주** | 정기 미팅과 마감 |
| 우측 — **절차 대기** | 트리거가 도래했는데 아직 실행하지 않은 절차 |

마일스톤 블록은 두지 않는다. 진행 중 업무가 그 역할을 대신한다.

### 4.2 나머지 화면

**업무** — 목록 뷰 / 칸반 뷰(`할 일 → 진행중 → 검토요청 → 완료`, 보류는 별도 영역). 「출처」로 *내 발의* / *요청받음* / *대표지시* / *절차* 등을 구분한다. 요청받은 건에만 요청자·부서·접수경로·회신기한·회신내용이 붙고, **회신을 해야 닫힌다.** 업무 상세에 체크리스트·지시사항 연결·기간·「이슈로 공유」 버튼.

**절차** — 절차 라이브러리(목록·상세·단계 편집), 실행이력(회차별), 예외 확인함.

**계획** — 주간(이번 주 목표, 요일별 배치, 회고) / 월간(이달 목표, 주차별 덩어리, 고정 일정) / 마일스톤(여러 지시사항을 아우르는 관문).

**기록** — 업무일지(§5.7) / 회의록(§5.8) / 전화메모 / 리포트(§5.5).

**기준** — 지시사항 / 인수인계 / 연락처 / 업체 관리 / 설정(업무영역 분류, 사내 용어집). **이 다섯은 전부 업체별로 갈린다.**

## 5. 핵심 동작

### 5.1 절차 — 이 제품의 1급 개념

**절차(procedure)는 "이 업무를 어떻게 하는가"의 정의다.** 업무(task)가 *"이번에 무엇을 했나"* 라면 절차는 *"이런 일은 이렇게 한다"* 이다.

절차 하나가 가진 것:

| 요소 | 예 (부가세 신고) |
|---|---|
| **트리거** | 주기 — 분기 종료 후 25일 이내 |
| **입력자료** | 이카운트 매출·매입 자료, 위하고 원장 |
| **단계** | 자료 추출 → 원장 대사 → 이상 항목 확인 → 세무대리인 확인 → 신고 → 증빙 보관 |
| **단계별 판단기준** | "대사 차이 10만원 초과 시 원인 규명 전 진행 금지" |
| **산출물** | 신고서, 대사표, 증빙철 |
| **AI 위임수준** | `사람만` / `AI 초안 → 내가 승인` / `AI 자동` |

**판단기준이 AI에게 가장 중요하다.** 단계 목록만 있으면 순서는 따라 하지만 "언제 멈춰야 하는지"를 모른다.

### 5.2 절차는 두 갈래로 생긴다

```
아는 업무 (부가세 신고, 월 마감…)    →  ① 처음부터 절차를 쓰고 시작한다
모르던 업무 (해보니 반복되더라)       →  ② 3회차에 툴이 초안을 제안한다
```

**②의 동작:**

```
1회차   그냥 업무를 한다. 체크리스트만 남는다.
2회차   같은 영역·유사 제목 감지 → "지난번과 같은 건가요?"
3회차   ✨ "이거 절차로 굳힐까요?" → 과거 체크리스트 3개를 합쳐 초안 자동 생성
        내가 다듬어 확정
4회차~  절차가 업무를 자동 생성한다. 실행이력이 자동으로 쌓인다.
```

**설계 원칙: 절차는 사람의 추가 노동이 아니라 부산물로 나와야 한다.** "절차를 문서로 쓰세요"라고 하면 아무도 쓰지 않는다. ②에서 사람이 하는 일은 3회차에 초안을 한 번 다듬는 것뿐이다.

### 5.3 반복업무는 절차의 한 종류다

> **반복업무 = 트리거가 「주기」인 절차**

매일·매주 빠지면 안 되는 체크 항목을 별도 개념으로 두지 않는다. 주기 트리거를 가진 절차로 만들면 **체크하는 행위 자체가 실행이력이 되어 학습 데이터가 된다.** 따로 SOP를 쓸 필요가 없다.

### 5.4 예외 — 사람이 적지 않는다

사람에게 "이번엔 뭐가 달랐는지 적으세요"라고 하면 적지 않는다. 그래서 **툴이 탐지하고 사람은 확인만 한다.**

> ⚠️ *"이번 8월 마감은 평소와 다릅니다 — 「세무대리인 확인」 단계를 건너뛰었고, 「원장 대사」에 평소의 3배가 걸렸습니다. 예외로 정리할까요?"*
> → **[예외 맞음]** 누르고 한 줄 덧붙이면 끝. **[정상임]** 을 누르면 사유가 남고 탐지 규칙 개선 대상이 된다.

**탐지 규칙 — `src/domain/`의 순수 함수. AI 없이 계산된다.**

| # | 규칙 | 조건 | 필요 표본 |
|---|---|---|---|
| 1 | 단계 건너뜀 | 절차의 필수 단계에 대응하는 실행 기록이 없음 | 1회차부터 |
| 2 | 단계 추가 | 절차에 없는 단계가 실행됨 | 1회차부터 |
| 3 | 소요시간 이탈 | 해당 단계 과거 중앙값의 2배 초과 또는 1/2 미만 | **3회 이상** |
| 4 | 산출물 누락 | 산출물이 정의된 단계인데 산출물이 없음 | 1회차부터 |
| 5 | 사람 개입 증가 | AI 위임 절차인데 사람 개입 단계 수가 이전 회차보다 늘어남 | **2회 이상** |
| 6 | 순서 뒤바뀜 | 정의된 순번과 실제 실행 순서가 다름 | 1회차부터 |

표본이 없으면 "평소"가 정의되지 않으므로 규칙 3·5는 회차가 쌓인 뒤에만 동작한다.

AI가 하는 일은 이 탐지 결과에 **설명 문장을 붙이는 것뿐**이고, 그건 경영관리서비스의 AI 호출로 나중에 붙인다. **AI가 없어도 탐지는 동작한다.**

이 방식은 경영관리 PRD의 **ISS-001(규칙 기반 자동 이슈 생성 → 사람 확인)** 과 같은 패턴이라 두 툴의 사고방식도 일관된다.

### 5.5 리포트와 성과평가

주간·월간·연간 리포트는 **밖으로 나가지 않는 내부 자료**다.

- **자동집계에 들어가는 것:** 완료 업무 수와 영역별 분포, 절차 확정 건수, 발행 이슈와 그 결과, 지연 건수, 예외 처리 건수, 반복업무 이행률
- **내가 쓰는 것:** 서술 (숫자가 설명하지 못하는 것)

**스냅샷으로 굳힌다.** 나중에 업무를 수정해도 지난 리포트는 변하지 않는다. 연말에 *"3월에 뭐 했더라"* 를 되짚을 수 있어야 하기 때문이다.

**성과평가 자료는 「AI가 대표 질문에 자동으로 답할 때 쓰는 근거」가 아니라 「내가 검토해서 내는 산출물」이다.** 이 구분을 지켜야 §7의 공개 정책이 무너지지 않는다.

### 5.6 인박스 — 외부에서 들어오는 모든 것의 착륙장

```
회의록에서 추출된 할 일          ┐
전화메모의 「조치할 것」           ├→ 인박스 →→ 업무로 승격 (기한·중요도 지정)
직접 던져둔 메모                  │              또는 버림
경영관리서비스의 이슈 회신·배정    ┘
```

대표 지시만 인박스를 건너뛴다(§2.3).

승격 시 제목이 길면(60자 초과) 제목은 자르고 전문은 상세에 보존한다.

### 5.7 업무일지 — 어제와 오늘을 잇는 장치

일지는 기록이 아니라 **어제와 오늘을 잇는 장치**다. 4단 구성이다.

| 섹션 | 입력 | 동작 |
|---|---|---|
| **1. 오늘 진행한 업무** | 자동 수집 | 그날 상태가 바뀐 업무와 체크한 항목을 모아 **스냅샷으로 굳힌다.** 나중에 업무를 수정해도 그날 일지는 바뀌지 않는다 |
| **2. 이슈 · 막힌 것** | 직접 | 다음날 「어제 이야기」에 올라온다 |
| **3. 내일 할 일** | 직접 | 줄마다 **「업무로」 체크박스.** 체크한 것만 업무로 등록(기한=내일)되어 다음날 「오늘 할 일」에 나타난다. 체크 안 한 것은 다음날 「어제 이야기」에 *메모로 남긴 것*으로 표시된다 |
| **4. 메모** | 직접 | — |

업체가 여럿이면 일지 한 장 안에서 업체별 섹션으로 나뉜다. 업체가 하나면 섹션 헤더 없이 보인다.

### 5.8 녹음 → 회의록

```
폰/PC에서 업로드 → Supabase Storage (status: 대기)
      ↓  로컬 워커가 감지 (Realtime 구독, 실패 시 30초 폴링으로 폴백)
  Whisper large-v3 전사 (로컬 PC GPU) → transcript 저장 → 음성 파일 삭제
      ↓
  요약 → 회의록 초안 + 할 일 추출
      ↓
  회의록 저장 · 할 일은 인박스로 · 프론트는 Realtime으로 진행률 표시
```

**사내 용어 교정** — 전사가 「타이백」으로 나와도 회의록에는 「타이벡」으로 적힌다. 용어집을 요약 단계에 함께 넘긴다. 용어집은 「기준 › 설정」에서 관리한다.

**민감 회의 정책** — 업로드 시 「민감」으로 표시하면

1. 전사 후 음성 파일 즉시 삭제
2. 자동 요약을 하지 않음
3. **전사문을 Supabase에 저장하지 않고 로컬 PC에만 둔다.** 클라우드에는 제목·일시·참석자만 남는다

회생·인사 회의용이다. 그 회의록 본문은 노트북·폰에서 볼 수 없다 — **자료 성격상 의도된 제약이다.**

**PC가 꺼져 있으면** 전사가 대기 상태로 쌓인다. 켜면 밀린 것부터 처리한다. 나머지 기능은 PC와 무관하게 동작한다.

### 5.9 업체 확장

사업체가 5개까지 늘어날 수 있다. 지금 대비해 둔다.

- 모든 테이블에 `company_id`
- **업체가 1개면 셀렉터를 숨긴다** — 화면이 단일 업체와 동일하게 보인다
- 2개째를 등록하면 사이드바 상단에 셀렉터가 나타난다
- 「오늘 할 일」은 기본 **전 업체 통합**, 업체 뱃지로 구분. 셀렉터로 한 업체만 필터
- 업무일지는 통합하되 일지 안에서 업체별 섹션으로 구분
- **지시사항·인수인계·연락처·업무영역·절차는 업체별로 완전히 분리한다**

### 5.10 이 툴에 들어가는 AI — 「작업 도우미」

AI가 두 곳에 들어가는데 **역할이 완전히 다르다.** 이걸 섞으면 설계가 무너진다.

| | **경영관리서비스의 AI** | **업무관리툴의 AI** (이 저장소) |
|---|---|---|
| 누구를 위해 | 대표 · 임원 · 담당자 | 나 (경영지원부장) |
| 무엇을 | 회사 데이터에 대한 **질의응답**, 보고서 | 내 업무를 돕는 **작업 도우미** |
| 형태 | 대화형 인터페이스 | 화면 안의 버튼 — 「초안 만들기」, 「예외 확인」 |

**이 툴의 AI가 하는 일 4가지**

| # | 기능 | 무엇을 | 언제 |
|---|---|---|---|
| 1 | **문서 초안 작성** | 사내 공지, 공문, 주기적 행정 신고 서류 | 절차의 산출물을 만들 때 |
| 2 | **절차(SOP) 추출** | 3회차 체크리스트를 합쳐 절차 초안 생성(§5.2) | 반복 감지 시 |
| 3 | **예외 설명** | 탐지된 이상(§5.4)에 "왜 달랐나" 설명을 붙임 | 예외 확인함 |
| 4 | **회의록 요약·용어 교정** | 전사문 → 회의록 초안 + 할 일 추출(§5.8) | 녹음 업로드 후 |

**공통 원칙: AI는 초안까지, 확정은 사람이 한다.** 어느 기능도 내 승인 없이 결과를 확정하지 않는다.

#### 문서 초안이 좋아지는 구조 — 이게 학습 층과 연결된다

```
문서 양식 (한 번 등록)  ┐
확정된 과거 문서들      ├→ AI → 초안 → 내가 수정 → 확정
이번 회차의 입력 자료   ┘                            │
        ▲                                            │
        └──────── 확정된 문서가 다음 초안의 참고자료가 된다 ───┘
```

**공문을 열 번 쓰면 열한 번째 초안이 눈에 띄게 좋아진다.** 문서가 곧 학습 데이터이기 때문이다. 이게 §5.1의 절차, §5.4의 예외와 같은 원리다 — **일하면 데이터가 쌓이고, 데이터가 쌓이면 AI가 더 잘한다.**

#### AI 없이도 동작하는 부분을 분리한다

| 부분 | 어디서 | AI 필요? |
|---|---|---|
| 예외 **탐지** (§5.4의 규칙 1~6) | `src/domain/exceptions.ts` — 순수 함수 | ❌ 불필요 |
| 예외 **설명 문장** | AI 호출 | ✅ 필요 |
| 절차 후보 **감지** (3회 반복) | `src/domain/` — 순수 함수 | ❌ 불필요 |
| 절차 **초안 문장** 생성 | AI 호출 | ✅ 필요 |
| 문서 초안 작성 · 회의록 요약 | AI 호출 | ✅ 필요 |

**계산으로 되는 것은 순수 함수로 둔다.** 테스트할 수 있고, AI가 죽어도 동작하고, 비용이 0이다. AI는 그 위에 **문장을 얹을 뿐**이다.

#### 호출 방식

**API 키를 브라우저에 넣지 않는다.** Supabase Edge Function을 거친다.

```
브라우저 → Supabase Edge Function → Claude API
           (여기에만 API 키가 있다)
```

기술 선택은 §8, 비용은 §8.2에 적었다.

| `directives` | 코드(D-01), 제목, 사업축, 영역, 출처(조항 번호), 요약, 근거, 기한, 중요도, 상태 |
| `tasks` | 제목, 상세, **출처**, 요청자·부서·경로·회신, 지시사항ID, **절차ID**, **실행ID**, 영역, 중요도, 상태, 시작일, 기한, **focus_date**, 진행률 |
| `checklist` | 업무ID, 항목, 필수여부, 완료 |
| `inbox` | 내용, 태그, 출처, 원본ID, 승격된 업무ID |

- `tasks.출처` = `내 발의` / `요청받음` / `일지` / `인박스` / `회의록` / **`대표지시`** / **`절차`**
- `tasks.상태` = `할 일` / `진행중` / `검토요청` / `완료` / `보류` (칸반은 `보류`를 제외한 4열)
- `inbox.출처` = `직접` / `회의록` / `전화메모` / **`경영관리서비스`**

### 6.2 학습 층 ★ 이 제품의 핵심

| 테이블 | 핵심 필드 |
|---|---|
| **`procedures`** | 코드, 제목, 영역, **트리거종류**(주기/이벤트/수동), 주기규칙, 입력자료(JSON), 산출물 양식, **AI 위임수준**, 버전, 상태(초안/확정/폐기), 생성경로(직접작성/자동제안) |
| **`procedure_steps`** | 절차ID, 순번, 제목, 하는 일, **판단기준**, 예상 소요(분), 필요 자료, 자동화 가능여부, 필수여부 |
| **`runs`** | 절차ID, **회차**, 대상기간, 시작시각, 종료시각, **수행자**(사람/AI/혼합), 결과(완료/중단), 업무ID |
| **`run_steps`** | 실행ID, 절차단계ID, 실제 소요(분), 산출물, 메모, **사람 개입 여부**, 완료시각, 실행순서 |
| **`exceptions`** | 실행ID, 실행단계ID(nullable), **탐지규칙**(§5.4의 1~6), 탐지 내용, 확인상태(대기/예외확정/정상), 내가 쓴 설명, 절차 반영 여부 |

**`AI 위임수준`은 지금부터 넣어둔다** — `사람만` / `AI 초안 → 내가 승인` / `AI 자동`. 나중에 AI를 붙일 때 이 스위치 하나로 넘긴다.

### 6.3 문서 층 — AI 초안이 만들어지고 쌓이는 곳

| 테이블 | 핵심 필드 |
|---|---|
| **`document_templates`** | 종류(공지/공문/신고서/보고서), 제목, 양식 본문, 필요 입력자료, 연결 절차ID, 버전 |
| **`documents`** | 양식ID, 실행ID(run_id), 제목, **AI 초안 본문**, **확정 본문**, 상태(초안/검토중/확정/폐기), 확정일, 참고한 과거 문서ID 목록 |

**초안과 확정본을 따로 둔다.** 둘의 차이가 *"AI가 뭘 놓쳤나"* 를 알려주는 학습 신호다 — 매번 같은 곳을 고치고 있으면 양식이나 프롬프트가 잘못된 것이다.

`documents`는 `runs`에 연결된다 — **문서는 절차 실행의 산출물**이기 때문이다(§5.10).

### 6.8 파생 규칙

- **오늘 할 일** = `due_date = 오늘` 또는 `focus_date = 오늘`, 상태 ≠ 완료
- **어제 이야기** = 전날 `daily_logs.issues` + 전날 완료된 `tasks` + 전날 `log_todos` 중 미체크 항목
- **진행 중 업무** = 상태가 완료·보류가 아닌 `tasks`를 `directive_id`로 묶고, 시작일=최소 시작일 / 마감일=최대 기한 / 진행률=평균
- **절차 대기** = 트리거가 도래했는데 해당 기간의 `runs`가 없는 `procedures`
- **절차 제안 후보** = 절차에 연결되지 않은 `tasks` 중 같은 영역·유사 제목이 3건 이상

## 7. 공개 정책 — 스키마에 못 박는다

내 업무는 비공개인데 AI는 그 데이터로 학습해서 대표 질문에 답한다. 그러면 *"이 건에 3주 썼다"* 같은 것이 답변에 간접적으로 새어 나갈 수 있다.

**학습에는 전부 쓰되, 답변 근거로 인용할 수 있는 것은 아래 표대로만 한다.**

| 테이블 | AI가 답변 근거로 **인용** | 이유 |
|---|---|---|
| `issue_publications` | ✅ 가능 | 내가 발행한 것 |
| `directives` | ✅ 가능 | 대표가 준 것 |
| `procedures` · `procedure_steps` | ❌ 불가 | 내 업무 노하우 |
| `runs` · `run_steps` · `exceptions` | ❌ 불가 | **"이 일에 3주 썼다"가 새어 나가는 자리** |
| `tasks` · `checklist` · `daily_logs` | ❌ 불가 | 비공개 작업 내역 |
| `documents` | ⚠️ **확정본만**, 그것도 발송·제출한 것만 | 초안은 미완성물이다 |
| `document_templates` | ❌ 불가 | 내 업무 노하우 |
| `periodic_reports` | ⚠️ 내가 **확정한 것만** | 성과평가 자료 |

이 표는 문서 주석이 아니라 **`disclosure_policy` 테이블로 DB에 넣는다.** 나중에 AI를 붙이는 사람이 이 문서를 안 읽어도 사고가 나지 않게 한다.

| 배포 | Vercel | 무료 |

**`src/domain/`은 Supabase와 React를 import하지 않는다.** 날짜 계산·정렬·집계·매핑·**예외 탐지**·**리포트 집계**가 전부 여기 모인다. DB나 브라우저 없이 테스트하기 위한 경계다. 이 경계가 무너지면 테스트가 느려지고 깨지기 쉬워진다.

**인증** — Supabase Auth 이메일 매직링크. 단독 사용이라 비밀번호 관리를 하지 않는다. 로컬 워커는 `service_role` 키가 아니라 전용 계정 토큰으로 붙는다.

**연동 방식은 이 문서에서 정하지 않는다.** 별도 「연동 계약서」에서 필드 단위로 정의한다. 경영관리서비스가 재정리 중이라 확정 전이다. → §14 OQ-02

### 8.1 디자인

`DESIGN-apple.md`의 토큰을 Tailwind v4의 `@theme` 블록에 심는다. (v4는 `tailwind.config.js`를 쓰지 않는다.)

- **Action Blue `#0066cc`가 유일한 인터랙티브 색이다.** 두 번째 액센트를 만들지 않는다. 기한 초과 경고(`#d70015`)만 예외로 두되 최소한으로 쓴다

- **카드·버튼·텍스트에 그림자를 넣지 않는다.** 밝은 면과 어두운 면의 교차가 구분선 역할을 한다

## 9. 수용 기준

**절차와 학습 — 이 제품의 핵심**

- [ ] 절차를 직접 작성하면 트리거 도래 시 업무가 자동 생성된다
- [ ] 업무를 완료하면 해당 회차의 실행이력(`runs`·`run_steps`)이 남는다
- [ ] 같은 영역·유사 제목 업무가 3건 쌓이면 절차 초안이 제안된다
- [ ] 제안된 초안에 과거 체크리스트 항목이 단계로 들어가 있다
- [ ] 반복업무를 별도 개념 없이 「주기 트리거 절차」로 만들 수 있다
- [ ] 회차가 3개 이상인 절차에서 소요시간이 중앙값의 2배를 넘으면 예외로 감지된다
- [ ] 필수 단계를 건너뛰면 회차가 1개여도 예외로 감지된다
- [ ] 감지된 예외를 「정상임」으로 처리하면 사유가 남고 규칙 개선 대상이 된다
- [ ] **예외 탐지가 AI 호출 없이 동작한다**

**업무와 연동**

- [ ] 업무 상세에서 「이슈로 공유」를 누르면 지정한 필드만 발행되고, 업무 제목·진행률·실행이력은 나가지 않는다
- [ ] 공유하지 않은 업무는 경영관리서비스에서 조회되지 않는다
- [ ] 대표 지시가 들어오면 인박스를 거치지 않고 업무로 등록되며 중요도가 `P0`이다
- [ ] 이슈 회신은 인박스로 들어오고, 인박스에서 업무로 승격된다
- [ ] 요청받은 업무는 회신 내용을 기록해야 닫힌다
- [ ] 진행 중 업무가 지시사항 단위로 묶여 시작일·마감일·D-day·진행률과 함께 타임라인으로 보인다

**하루의 흐름**

- [ ] 일지의 「내일 할 일」에서 체크한 항목만 다음날 「오늘 할 일」에 나타난다. 체크 안 한 항목은 「어제 이야기」에 메모로 표시된다
- [ ] 전날 일지의 「이슈·막힌 것」이 다음날 「어제 이야기」에 그대로 올라온다
- [ ] 「오늘 진행한 업무」는 스냅샷이라 이후 업무를 수정해도 변하지 않는다

**문서와 AI**

- [ ] 문서 양식을 등록하면 절차 실행 시 「초안 만들기」로 초안이 생성된다
- [ ] 생성된 초안을 수정해 확정할 수 있고, **초안과 확정본이 둘 다 남는다**
- [ ] 다음 회차 초안 생성 시 과거 확정본이 참고자료로 들어간다
- [ ] **AI가 만든 것은 무엇이든 내 확정 없이 발송·제출되지 않는다**
- [ ] `ANTHROPIC_API_KEY`가 브라우저 번들에 포함되지 않는다 (Edge Function 경유)
- [ ] AI 호출이 실패해도 업무·절차·실행이력 기록은 정상 동작한다

**리포트**

- [ ] 주간·월간 리포트가 자동집계로 생성되고 내가 서술을 덧붙일 수 있다
- [ ] 확정한 리포트는 이후 업무를 수정해도 변하지 않는다
- [ ] 연간 리포트에서 영역별 업무 분포와 절차 확정 건수를 볼 수 있다

**녹음 (7단계)**

- [ ] 폰에서 녹음 파일을 올리면 PC 워커가 전사하고 회의록 초안이 생성된다
- [ ] 「민감」 표시한 회의는 전사문이 Supabase에 저장되지 않고 음성이 삭제된다
- [ ] 사내 용어가 회의록에서 올바르게 교정된다

**공통**

- [ ] 본인 데이터만 조회된다 (RLS)
- [ ] 업체가 1개일 때 셀렉터가 보이지 않고, 2개째 등록 시 나타난다
- [ ] `src/domain/`이 Supabase·React를 import하지 않는다

## 10. 위험과 대응

| 위험 | 대응 |
|---|---|
| **절차를 아무도 안 쓴다** — 가장 큰 위험 | 절차를 부산물로 만든다(§5.2). 직접 작성은 「아는 업무」에만 요구하고, 나머지는 3회차 자동 제안 |
| **예외가 기록되지 않는다** | 사람이 적지 않게 한다. 툴이 탐지하고 사람은 확인만(§5.4) |
| **탐지 규칙이 오탐만 낸다** | 「정상임」 처리 시 사유를 남기고 규칙 개선 대상으로 연결. 임계값은 실데이터를 보고 조정 → §14 OQ-06 |
| **두 툴이 같은 것을 두 번 만든다** | 연동 계약서를 **경영관리서비스 재정리 전에** 넘긴다(§2.4) |
| **AI 답변에 내 업무 내역이 새어 나간다** | §7 공개 정책을 `disclosure_policy` 테이블로 DB에 못 박는다 |
| **AI 초안을 그대로 내보내 사고가 난다** — 행정 신고 서류라 틀리면 실제 불이익 | 확정 단계를 반드시 거치게 한다(§5.10). 초안은 **초안 상태 그대로 발송 불가**. 금액·기한·법령 인용은 사람이 눈으로 확인 |
| **AI가 그럴듯한 거짓을 쓴다**(환각) | 입력 자료를 프롬프트에 명시적으로 넣고, 초안에 **근거가 된 자료를 함께 표시**한다. 근거 없는 문장은 내가 지운다 |
| **API 키 유출** | Edge Function 경유(§5.10). 브라우저에 키를 넣지 않는다. `service_role` 키는 어디에도 쓰지 않는다 |
| **AI 호출 실패·지연으로 업무가 막힌다** | AI는 **부가 기능**이다. 탐지·감지·집계는 순수 함수라 AI 없이 동작한다(§5.10) |
| **AI 비용이 예상을 넘는다** | 월 1만원 수준으로 추정되나(§8.2) 실사용으로 재측정한다. Edge Function에서 호출 건수·토큰을 기록한다 |
| 날짜 경계 로직 오류 (주기 트리거, 일지→업무, 주·월 경계) | 순수 함수로 분리하고 테스트 필수. `daysUntil`은 `Math.floor`가 아니라 `Math.round` — 서머타임 전환 때 두 로컬 자정 사이가 23시간 또는 25시간이 되는데 `round`가 그 ±1시간을 흡수한다 |
| GPU 전사 환경(CUDA·cuDNN·ffmpeg) 설치가 까다롭다 | CPU 모드로 자동 폴백. 워커가 죽어도 앱 나머지는 정상 동작하도록 분리 |
| PC가 꺼져 있으면 전사가 대기 | 의도된 동작. 켜면 밀린 것부터 처리. 대기 건수를 화면에 표시 |
| Supabase 무료 티어는 1주일 미접속 시 일시정지 | 매일 사용이 전제라 실무상 문제 없음 |
| Storage 무료 1GB (1시간 녹음 = 30~60MB) | 전사 완료 후 음성 파일 자동 삭제 |
| 업무 데이터가 외부 클라우드에 저장됨 | 회사가 이미 외부 SaaS를 사용 중. 민감 회의는 §5.8 정책으로 분리 |
| 사업이해자료(사외 반출 금지)의 유출 | 원본 문서를 이 저장소에 들이지 않는다. 인용이 필요하면 조항 번호만 참조한다 |

## 11. 검증 방법

- **순수 로직은 Vitest로 단위 테스트.** 예외 탐지·리포트 집계·주기 트리거 계산·일지→업무 승격·인박스 승격·정렬·D-day·지시사항 집계
- **테스트 픽스처는 로컬 벽시계 리터럴을 쓴다.** `new Date(2026, 7, 11, 9, 0)` ○ / `new Date('2026-08-11T09:00:00+09:00')` ✕
  ISO 문자열은 절대 시각을 고정하는데 구현은 로컬 달력일을 본다. UTC 오프셋이 음수인 지역(미국 등)에서 하루가 밀려 테스트가 깨진다.
- **Windows의 Node는 `TZ` 환경변수를 무시한다.** `TZ=America/New_York npm test`로 시간대 테스트를 했다고 믿으면 안 된다
- Supabase 마이그레이션은 SQL 파일로 버전 관리. **Docker가 없어 로컬 스택(`supabase start`)을 쓰지 못하므로** 클라우드 프로젝트에 `npx supabase db push`로 올린다
- RLS 정책 테스트 — 다른 사용자 데이터가 조회되지 않는지
- `supabase gen types`로 DB 타입을 자동 생성해 계약 불일치를 컴파일 단계에서 차단
- 워커는 pytest + 목(mock). 실제 Whisper 호출 없이 상태 전이 검증
- **AI 호출은 목(mock)으로 테스트한다.** 실제 Claude 호출 없이 Edge Function의 입출력 형식·오류 처리·실패 시 폴백을 검증한다. **초안의 품질은 자동 테스트로 검증되지 않으므로**, 초안과 확정본의 차이(§6.3)를 눈으로 보고 프롬프트를 고치는 것이 유일한 방법이다

## 12. 초기 데이터

업체 하나(제우스)와 사업이해자료에서 도출한 시드를 넣는다. **금액·수치는 시드에 넣지 않는다** — 확정 회계수치가 아니라 원장·실사로 대사해야 할 참고값이고, 경영관리서비스가 다룰 영역이다.

- **지시사항** — 사업이해자료 §9의 7가지(D-01~D-07)와 §7 승급률, §5-3 현장손익, §6-3 축3 대사, §13 현금표, §10 회생지원, §4-1 제조업 여부 점검 (총 13건). **조항 번호와 제목만 넣고 본문은 옮기지 않는다**
- **인수인계** — §11의 부서 면담, 시스템 계정, 자료 인수 (총 13건)
- **마일스톤** — 첫 30일 주차별 관문, 품목·가격 기준 확정, 재고 실사, 회생 지원 종료
- **연락처** — §11의 담당자 목록. **실명 대신 역할·부서로 넣는다**
- **용어집** — §12 용어집 (타이벡·유공타이벡·마더롤·슬리팅·원지정비·승급률·이카운트·위하고 등)
- **업무영역** — 인수인계 / 품목·가격 / 원가·단위 / 재고 / 축별손익 / 현장손익 / 자금·현금 / 회계·세무 / 회생지원 / 데이터·지표 / 보고·마감
- **절차** — 시드에 넣지 않는다. 아는 업무부터 직접 작성한다(§5.2)
- **문서 양식** — 시드에 넣지 않는다. 3단계에서 실제 서식을 보고 등록한다(§14 OQ-08·OQ-09)

## 13. 로드맵

한 번에 다 만들지 않는다. **각 단계가 끝나면 그 시점부터 실제로 쓸 수 있어야 한다.**

| 단계 | 범위 | 끝나면 할 수 있는 것 |
|---|---|---|
| **1. 뼈대와 업무** | 스키마 + RLS, 인증, 6탭 껍데기, 애플 디자인 토큰, 업무 CRUD·목록·칸반, 지시사항, 인박스, 시드 | 인박스에 던져두고 업무로 승격해 칸반으로 굴린다 |
| **2. 절차와 실행이력** ⭐ | `procedures`·`procedure_steps`·`runs`·`run_steps`, 절차 직접 작성, 절차 → 업무 자동 생성, 반복업무 흡수 | **아는 업무를 절차로 정의하고 실행이력이 쌓이기 시작한다** |
| **3. 문서와 AI 초안** ⭐ | `document_templates`·`documents`, Edge Function(`draft`), 문서 초안 생성 → 수정 → 확정, 과거 확정본 참조 | **공지·공문·행정 신고 서류 초안이 자동으로 나온다.** 쓸 때마다 좋아진다 |
| **4. 하루의 흐름** | 「오늘」 화면 전체, 업무일지 4단, 어제 이야기, 일지 → 업무 승격 | 아침에 열고 퇴근 전 기록하는 사이클 완성 |
| **5. 예외와 리포트** | 예외 탐지(순수 로직) + 설명(AI), 예외 확인함, 3회차 절차 제안(AI), 주간·월간·연간 리포트 | 학습 데이터가 스스로 정리된다. 성과평가 자료가 나온다 |
| **6. 경영관리서비스 연동** | 이슈 발행, 대표 지시 수신 → P0 업무 직행, 회신 → 인박스 | 두 툴이 붙는다 |
| **7. 계획·기준·녹음** | 주간·월간 계획, 마일스톤, 인수인계·연락처, 회의록·녹음 전사·요약(AI), 민감 회의 정책 | 폰 녹음이 회의록이 되고, 주 단위 계획과 보고 자료 추출이 된다 |

1단계의 인박스는 **직접 던져둔 메모**만 받는다. 회의록·전화메모에서 흘러드는 경로는 7단계, 경영관리서비스에서 흘러드는 경로는 6단계에서 붙는다.

**AI는 3단계에서 처음 들어온다.** 그 전까지는 AI 없이 동작한다.

**업체 셀렉터 UI는 실제로 두 번째 업체가 생길 때 붙인다.** `company_id`는 1단계부터 모든 테이블에 넣되 화면에 노출하지 않는다.

### 13.1 2·3단계를 앞에 둔 이유 — 이번 로드맵의 핵심 판단

일반적인 업무 도구라면 「오늘」 화면과 업무일지가 2단계에 와야 한다. 하루의 흐름이 제품의 얼굴이기 때문이다. 그런데 뒤로 미뤘다.

> **이 제품의 목적은 AI 학습 데이터를 쌓는 것인데, 절차와 실행이력이 없으면 아무리 오래 써도 데이터가 안 쌓인다.**

「오늘」 화면이 없어도 업무는 굴러간다. 하지만 절차가 없으면 6개월을 써도 남는 것은 제목과 완료일뿐이다.

**데이터가 쌓이기 시작하는 시점을 최대한 앞당기는 것**이 이 제품에서 가장 중요한 일정 판단이다.

**3단계(문서와 AI 초안)를 그 바로 뒤에 둔 이유는 다르다 — 체감 가치다.** 행정 신고 서류 초안이 자동으로 나오는 것은 첫날부터 시간을 아껴준다. 그리고 그 문서들이 다시 학습 데이터가 되므로(§5.10), 2단계와 같은 논리로 **일찍 시작할수록 이득이 복리로 붙는다.**

### 13.2 6단계를 뒤에 둔 이유

경영관리서비스가 재정리 중이라 계약이 확정되지 않았다. 확정 안 된 상대와 붙이면 두 번 만든다. **문서(연동 계약서)는 지금, 구현은 6단계에** — 이렇게 나눈다.
