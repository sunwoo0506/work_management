## 0. 한 장 요약 — 개발을 몰라도 읽을 수 있게

두 개의 도구가 있습니다.

| | **업무관리툴** | **경영관리서비스** |
|---|---|---|
| 누가 쓰나 | 경영지원부장 1인 + AI | 대표 · 임원 · 관련 담당자 |
| 무엇이 있나 | 내 업무·절차·실행이력·문서 | 회사 숫자·이슈·보고서 |
| 기본 공개 | **비공개** | 관련자에게 공개 |

**이 문서는 두 도구 사이로 오가는 것을 항목 하나 단위까지 정해둔 약속입니다.**

오가는 것은 **딱 두 갈래**입니다.

```
   업무관리툴                                    경영관리서비스
  ┌──────────┐                                  ┌──────────┐
  │          │ ──① 이슈 발행 (내가 버튼 누를 때)─▶│  이슈     │
  │  내 업무  │                                  │  관리대장 │
  │          │ ◀─② 대표 지시 · 이슈 회신 ─────────│           │
  └──────────┘                                  └──────────┘
```

**중요한 원칙 3가지**

1. **①은 내가 「이슈로 공유」 버튼을 눌러야만 나갑니다.** 자동으로 나가는 게 하나도 없습니다
2. **내 업무 제목·진행률·소요시간은 절대 안 나갑니다.** 무엇을 얼마나 오래 했는지는 내 것입니다
3. **②로 들어온 것 중 대표 지시만 곧바로 업무가 되고**, 나머지는 인박스(분류 전 메모함)에 담깁니다

## 1. 왜 이 문서가 필요한가

두 도구가 **각자 따로 설계됐고, 업무 관리 기능을 양쪽 다 만들고 있었습니다.**

경영관리서비스 PRD의 §5.0.1 「업무관리 탭」이 업무 등록·칸반·마일스톤·체크리스트·반복업무·지연관리를 전부 **P0(없으면 안 되는 필수)** 로 명세하고 있고, 데이터 모델 §7.1에 `WorkItem`·`Milestone`·`ChecklistItem`이 있습니다. 이것이 업무관리툴이 만들려는 것과 **정면으로 겹칩니다.**

같은 업무가 두 곳에 있으면

1. 매일 어긋납니다 — "칸반에서 옮겼는데 왜 저기선 안 옮겨졌지"
2. **AI가 오염된 데이터를 학습합니다.** 업무관리툴은 학습이 목적인 도구라 이건 치명적입니다

**그래서 이 계약서가 하는 일은 두 가지입니다.**

- **경계를 못 박는다** — 무엇이 어느 쪽 소유인지
- **오가는 것을 항목 단위로 고정한다** — 나중에 "이 필드 있는 줄 알았는데" 가 없도록

## 2. 소유권 — 무엇이 어느 쪽 것인가

| 데이터 | 소유 | 상대는 |
|---|---|---|
| 업무 · 절차 · 실행이력 · 예외 · 체크리스트 | **업무관리툴** | 볼 수 없음 |
| 업무일지 · 인박스 · 회의록 · 전화메모 | **업무관리툴** | 볼 수 없음 |
| 문서 양식 · 문서 초안 | **업무관리툴** | 볼 수 없음 |
| 주간·월간·연간 리포트 | **업무관리툴** | 볼 수 없음 |
| 숫자 (손익 · 재고 · 현금 · 지표) | **경영관리서비스** | 만지지 않음 |
| 이슈 관리대장 | **경영관리서비스** | 발행만 함 |
| 대표 알림 · 보고서 | **경영관리서비스** | 관여하지 않음 |
| 외부 시스템 연동 (이카운트 · 위하고 · 은행) | **경영관리서비스** | 관여하지 않음 |
| 지시사항 | **양쪽에 각각 존재** | §5.2 참고 |

### 2.1 경영관리서비스에 요청하는 변경

아래를 제거하고, 필요하면 업무관리툴을 조회하는 화면으로 대체해 주십시오.

| 대상 | 사유 |
|---|---|
| §5.0.1 WRK-001 ~ WRK-010 (업무 등록·칸반·마일스톤·체크리스트·반복업무·지연관리) | 업무관리툴이 소유 |
| §5.0.2 · §5.0.3의 업무탭 실행 기능 | 위와 동일 |
| §7.1의 `WorkItem` · `Milestone` · `ChecklistItem` | 위와 동일 |

> 💡 **덧붙이자면 이 변경은 PRD 내부 모순도 함께 해소합니다.**
> §1.4 비목표에 *"구매·영업·현장 담당자가 매일 접속해 업무를 처리하는 부서별 운영시스템"*과 *"현업 부서의 프로젝트 관리 도구 대체"*를 하지 않는다고 선언해 놓고, §5.0.3에서 정확히 그것을 명세하고 있습니다.

### 2.2 이슈 관리는 그대로 둡니다

**§5.0의 이슈 관리(ISS-001 ~ ISS-014)는 전부 경영관리서비스가 소유합니다.** 업무관리툴은 여기에 **이슈를 하나 넣는 것**만 합니다 — PRD의 **ISS-002(수동 이슈 등록)** 자리입니다. 그쪽 PRD를 고치지 않아도 붙습니다.

## 3. 연결 방식

### 3.1 전제 — 각자 DB, API로만 대화

```
[업무관리툴]                          [경영관리서비스]
 브라우저 (React)                      Streamlit 등
      │                                     │
 Supabase (자체 DB)                   자체 DB
      │                                     │
 Edge Function ◀──── HTTPS ────▶ 수신 엔드포인트
 (수신 + 발신)                       (수신 + 발신)
```

- **DB를 공유하지 않습니다.** 서로의 창고를 직접 들여다볼 수 없습니다
- **양쪽이 수신 창구를 하나씩 열고, 서로 밀어 넣습니다** (push 방식)
- 업무관리툴 쪽 창구는 **Supabase Edge Function**입니다. 브라우저가 꺼져 있어도 받습니다

> **왜 DB 공유(안 A)가 아니라 이 방식인가**
> 창고를 공유하면 붙이기는 쉽지만 **경계가 흐려집니다.** "저쪽 테이블 하나만 읽자"가 쌓이면 결국 지금과 같은 중복 상태로 돌아갑니다. 그리고 이 계약서는 **안 A로 바꿔도 그대로 유효**하지만, 반대는 다시 써야 합니다.

### 3.2 주소

| 방향 | 주소 | 정하는 쪽 |
|---|---|---|
| 업무관리툴 → 경영관리서비스 | `POST {MGMT_BASE_URL}/api/v1/issues/inbound` | **경영관리서비스** (미정) |
| 경영관리서비스 → 업무관리툴 | `POST {WM_BASE_URL}/functions/v1/inbound` | 업무관리툴 (Supabase Edge Function) |

**둘 다 HTTPS만 허용합니다.**

### 3.3 인증

**공유 비밀키 방식**을 씁니다. 방향마다 **다른 키**를 씁니다.

| 방향 | 헤더 | 키 보관 위치 |
|---|---|---|
| 업무관리툴 → 경영관리서비스 | `X-Api-Key: {WM_TO_MGMT_KEY}` | 업무관리툴: Edge Function 환경변수 |
| 경영관리서비스 → 업무관리툴 | `X-Api-Key: {MGMT_TO_WM_KEY}` | 경영관리서비스: 서버 환경변수 |

**지켜야 할 것**

- **키를 코드나 저장소에 넣지 않습니다.** 양쪽 다 환경변수로만 둡니다
- **브라우저에 키가 들어가지 않습니다.** 업무관리툴의 발신은 반드시 Edge Function을 거칩니다
- 키가 틀리면 `401`을 반환하고 **본문을 처리하지 않습니다**
- 키 교체는 양쪽 합의 후 진행합니다. 교체 중에는 구·신 키를 동시에 받는 기간을 둡니다

## 4. 계약 ① — 이슈 발행 (업무관리툴 → 경영관리서비스)

### 4.1 언제 일어나나

사용자가 업무 상세 화면에서 **「이슈로 공유」 버튼을 누를 때만** 일어납니다. 그 외에는 어떤 경우에도 자동 발행하지 않습니다.

### 4.2 요청

```
POST {MGMT_BASE_URL}/api/v1/issues/inbound
Content-Type: application/json
X-Api-Key: {WM_TO_MGMT_KEY}
```

```json
{
  "contract_version": "1.0",
  "source": "work-management",
  "source_event_id": "pub_01HQ8ZK3M2XN4P7R",
  "occurred_at": "2026-08-09T14:30:00+09:00",
  "company_code": "jeus",

  "issue": {
    "title": "타이벡 재고 실사 차이 3건 미해소",
    "body": "8월 5일 실사에서 장부와 실물 차이가 3건 확인됐고, 담당 부서 회신이 2주째 없습니다.",
    "fact_or_estimate": "사실",
    "area": "재고",
    "severity": "높음",
    "directive_code": "D-04",
    "financial_impact": {
      "amount": null,
      "currency": "KRW",
      "basis": "미산정 — 처분가 확정 전"
    },
    "requested_decision": "처분 여부와 담당 부서 지정을 결정해 주십시오",
    "evidence": [
      { "label": "재고 실사표 2026-08-05", "note": "실사 담당자 서명본" },
      { "label": "구매사업본부 요청 이력", "note": "7/26, 8/2 두 차례 요청" }
    ]
  }
}
```

### 4.3 필드 정의

**봉투(어느 요청이든 공통)**

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `contract_version` | 문자열 | ✅ | 이 계약서의 버전. 현재 `"1.0"` |
| `source` | 문자열 | ✅ | 항상 `"work-management"` |
| `source_event_id` | 문자열 | ✅ | **중복 방지 열쇠.** 업무관리툴이 만든 발행 기록의 고유번호 |
| `occurred_at` | ISO 8601 | ✅ | 사용자가 발행 버튼을 누른 시각. **시간대 포함 필수** |
| `company_code` | 문자열 | ✅ | 어느 사업체인지. 값 체계는 §7 미확정 |

**이슈 본문**

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `title` | 문자열 (≤120자) | ✅ | 이슈 제목 |
| `body` | 문자열 (≤4000자) | ✅ | 핵심 내용 |
| `fact_or_estimate` | `사실` \| `추정` | ✅ | **확인된 사실인지 추정인지.** 이 구분이 없으면 대표가 추정을 확정으로 읽는다 |
| `area` | 문자열 | ✅ | 업무영역. 값 목록은 §7 미확정 |
| `severity` | `치명적` \| `높음` \| `중간` \| `낮음` | ✅ | 심각도 |
| `directive_code` | 문자열 \| `null` | — | 연결된 지시사항 코드 (`"D-04"` 등). 없으면 `null` |
| `financial_impact.amount` | 정수 \| `null` | ✅ | **원 단위 정수.** 산정 못 했으면 `null` |
| `financial_impact.currency` | 문자열 | ✅ | 항상 `"KRW"` |
| `financial_impact.basis` | 문자열 | ✅ | 그 금액의 근거, 또는 `null`인 이유 |
| `requested_decision` | 문자열 (≤500자) | ✅ | 무엇을 결정해 달라는 것인가 |
| `evidence[]` | 배열 | — | 근거 목록. `label`(무엇인지) + `note`(부연) |

> ⚠️ **`financial_impact.amount`에 대한 주의**
> 이 숫자는 **사용자가 발행 시점에 손으로 적은 값**이며 **확정 회계수치가 아닙니다.**
> 업무관리툴은 숫자를 집계하지 않습니다(설계서 §1.3). 확정값은 경영관리서비스가 원장 대사로 만듭니다.
> 경영관리서비스는 이 값을 **「추정·미검증」으로 표시**해야 합니다.

### 4.4 절대 보내지 않는 것

**아래 항목이 페이로드에 들어가면 계약 위반입니다.** 업무관리툴은 발송 직전에 이 목록을 검사합니다.

| 안 보내는 것 | 이유 |
|---|---|
| 업무 제목 · 업무 ID | 내 업무 내역은 비공개 |
| 진행률 · 상태 · 체크리스트 | 위와 동일 |
| **소요시간 · 실행이력 · 회차** | **"이 건에 3주 썼다"가 새는 자리** |
| 절차 · 절차 단계 · 판단기준 | 내 업무 노하우 |
| 업무일지 · 인박스 내용 | 비공개 작업 내역 |
| 문서 초안 (확정 전) | 미완성물 |
| 예외 사례 | 비공개 |

### 4.5 응답

**성공 (`200`)**

```json
{
  "external_issue_id": "ISS-2026-0142",
  "status": "신규",
  "received_at": "2026-08-09T14:30:02+09:00"
}
```

| 필드 | 설명 |
|---|---|
| `external_issue_id` | 경영관리서비스가 부여한 이슈 번호. **업무관리툴이 저장합니다** |
| `status` | 접수 직후의 이슈 상태 |
| `received_at` | 접수 시각 |

**중복 (`200`)** — 같은 `source_event_id`가 이미 있으면 **새로 만들지 않고** 기존 결과를 그대로 반환합니다. 오류가 아닙니다.

**실패**

| 코드 | 뜻 | 업무관리툴의 처리 |
|---|---|---|
| `400` | 필드가 규격에 안 맞음 | 재시도하지 않음. 발행 실패로 기록하고 사용자에게 표시 |
| `401` | 키가 틀림 | 재시도하지 않음. 설정 오류로 기록 |
| `409` | 업무 규칙 위반 (예: 종결된 이슈에 발행) | 재시도하지 않음 |
| `5xx` / 응답 없음 | 상대 장애 | **재시도** (§6.2) |

## 5. 계약 ② — 지시·회신 수신 (경영관리서비스 → 업무관리툴)

### 5.1 요청

```
POST {WM_BASE_URL}/functions/v1/inbound
Content-Type: application/json
X-Api-Key: {MGMT_TO_WM_KEY}
```

```json
{
  "contract_version": "1.0",
  "source": "jeus-management",
  "source_event_id": "evt_20260809_0087",
  "occurred_at": "2026-08-09T16:05:00+09:00",
  "company_code": "jeus",
  "type": "대표지시",
  "payload": { }
}
```

`type`은 셋 중 하나입니다.

| `type` | 무엇인가 | 업무관리툴에서 어떻게 되나 |
|---|---|---|
| **`대표지시`** | 대표가 내린 확정 지시 | 🔴 **인박스를 건너뛰고 바로 업무로 등록. 중요도 `P0`** |
| **`이슈회신`** | 내가 발행한 이슈에 달린 회신 | 📥 인박스로 |
| **`이슈배정`** | 경영관리서비스가 나에게 배정한 이슈 | 📥 인박스로 |

> **왜 대표 지시만 인박스를 건너뛰나**
> 이미 확정된 지시라 분류할 필요가 없고, 인박스에 섞이면 우선순위가 묻히기 때문입니다.

### 5.2 `type: "대표지시"`의 payload

```json
{
  "title": "8월 말까지 불용재고 처분계획 수립",
  "body": "재고 실사 결과를 반영해 처분 대상과 예상 처분가를 정리할 것.",
  "due_date": "2026-08-31",
  "directive_code": "D-04",
  "external_issue_id": "ISS-2026-0142",
  "issued_at": "2026-08-09T16:00:00+09:00",

```

| `directive_code` | 문자열 \| `null` | — | 지시사항 코드. **업무관리툴에도 같은 코드의 지시사항이 있으면 연결합니다** |
| `external_issue_id` | 문자열 \| `null` | — | 어느 이슈에서 나온 지시인지 |
| `issued_at` | ISO 8601 | ✅ | 지시가 내려진 시각 |
| `issued_by_role` | 문자열 | ✅ | **역할로 적습니다.** 실명 금지 — `"대표"`, `"경영지원 관리자"` |

**업무관리툴이 만드는 업무**

| 항목 | 값 |
|---|---|
| 출처 | `대표지시` |
| 중요도 | **`P0`** |
| 상태 | `할 일` |
| 기한 | `due_date` |
| 지시사항 연결 | `directive_code`가 일치하면 연결, 없으면 비움 |

> **지시사항 코드는 양쪽이 같은 체계를 씁니다** — `D-01` ~ `D-13`. 어느 쪽이 원본인지는 §7 미확정입니다.

### 5.5 응답

**성공 (`200`)**

```json
{

  "created": { "kind": "task", "id": "tsk_01HQ..." },
```

`created.kind`는 `"task"`(대표지시) 또는 `"inbox"`(그 외)입니다.

**실패** — §4.5와 같은 규칙입니다. `5xx`만 재시도 대상입니다.

## 6. 공통 규칙

### 6.1 중복 방지 — `source_event_id`

**양쪽 다 `source_event_id`를 저장하고, 같은 값이 다시 오면 처리하지 않습니다.**

네트워크가 끊기면 보낸 쪽은 "실패했나?" 싶어 다시 보냅니다. 그때 받은 쪽이 두 번 처리하면 **같은 업무가 두 개 생깁니다.** 이 열쇠 하나로 막습니다.

```
받음 → source_event_id 이미 있나?
         ├─ 있음 → 처리하지 않고 기존 결과 그대로 반환 (200)
         └─ 없음 → 처리하고 결과 저장
```

### 6.2 실패했을 때

| 상황 | 어떻게 |
|---|---|
| `5xx` 또는 응답 없음 | **3회까지 재시도.** 간격 10초 → 60초 → 300초 |
| 3회 다 실패 | 발송 기록을 `발송실패`로 두고 **화면에 표시.** 사용자가 수동으로 다시 시도 |
| `4xx` | **재시도하지 않습니다.** 규격이 틀렸거나 키가 틀린 것이라 다시 보내도 같은 결과입니다 |

**자동 재시도는 여기까지입니다.** 무한 재시도 큐를 만들지 않습니다 — 하루 몇 건 수준의 트래픽이라 사람이 다시 누르는 게 더 확실합니다.

### 6.3 순서

**순서를 보장하지 않습니다.** 받는 쪽은 `occurred_at`을 보고 판단합니다.

이미 처리한 것보다 오래된 `occurred_at`이 뒤늦게 도착하면 **기록은 남기되 상태는 덮어쓰지 않습니다.**

### 6.4 시각

- 모든 시각은 **ISO 8601 + 시간대 포함**입니다 — `2026-08-09T14:30:00+09:00`
- 날짜만 있는 필드(`due_date`)는 `YYYY-MM-DD`이고 **한국 시간 기준 달력일**입니다

> ⚠️ 시간대를 뺀 `2026-08-09T14:30:00` 같은 값은 **받지 않습니다**(`400`). 이 프로젝트는 시간대 때문에 실제로 결함이 났던 적이 있습니다.

### 6.5 실명 금지

**양쪽 다 페이로드에 사람 이름을 넣지 않습니다.** 역할·부서로 적습니다.

| ✕ | ○ |
|---|---|
| `"홍길동 과장"` | `"구매사업본부 담당자"` |
| `"김대표"` | `"대표"` |

두 저장소 모두 외부 서버(GitHub)에 올라가고, 이 페이로드는 로그에 남습니다.

### 6.6 계약 버전

`contract_version`으로 관리합니다.

| 변경 | 버전 |
|---|---|
| 필드 **추가** (선택 항목) | 올리지 않음. 받는 쪽은 모르는 필드를 무시합니다 |
| 필드 **삭제**, 이름 변경, 의미 변경 | **올림** (`1.0` → `2.0`) |
| 필수 여부 변경 | **올림** |

받는 쪽은 모르는 `contract_version`이 오면 `400`을 반환하고 처리하지 않습니다.

### 6.7 로그

## 8. 이번 버전에서 하지 않는 것

명시적으로 범위 밖입니다. 필요해지면 계약 버전을 올려 추가합니다.

- **숫자 데이터 교환** — 손익·재고·현금 수치는 오가지 않습니다
- **업무관리툴의 업무를 경영관리서비스가 조회하는 기능** — 발행한 이슈만 저쪽에 존재합니다
- **실시간 동기화** — 이벤트가 생길 때만 한 번씩 보냅니다
- **양방향 상태 동기화** — 이슈 상태의 원본은 경영관리서비스 한 곳입니다
- **첨부파일 전송** (IC-08)
- **주간·월간 리포트 전송** — 이건 업무관리툴 내부 자료입니다
