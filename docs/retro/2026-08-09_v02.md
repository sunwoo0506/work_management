## 🛠 작업 상세

### 1. 설계서를 다시 쓰고, 기존 설계서는 흡수 후 삭제

- **무엇을:** 800줄짜리 새 설계서를 쓰고, 기존 설계서에서 필요한 부분(화면 구성, 업무일지 4단 구성, 녹음→회의록 흐름, 민감 회의 정책 등)을 옮겨 담은 뒤 기존 파일은 삭제했습니다. 원본은 git(작업 기록을 순서대로 보관하는 장치)에 영구히 남아 있습니다.
- **왜:** 제품 정의가 바뀌었는데 기존 문서를 부분 수정하면, 앞뒤가 안 맞는 문장이 곳곳에 남습니다. 그리고 설계서가 두 개면 **"어느 쪽이 진짜지?"** 라는 문제가 생깁니다.
- **결과:** 유효한 설계서가 하나뿐입니다. "무엇이 바뀌었나"는 이 회고가 대신 기록합니다.

### 2. 「절차」와 「실행이력」을 제품의 중심 개념으로

- **무엇을:** 지금까지는 「업무」가 중심이었는데, 여기에 **「절차」**(이런 일은 이렇게 한다)와 **「실행이력」**(이번엔 실제로 어떻게 했나), **「예외」**(절차대로 안 됐을 때 왜 그랬나)를 추가했습니다.
- **왜:** 제목·상태·기한만 쌓아서는 사람이든 AI든 그 일을 넘겨받을 수 없습니다. 부가세 신고를 대신하려면 *"어떤 자료를 어디서 뽑아서, 무슨 순서로, 무엇을 확인하고, 어떤 양식으로 냈는가"* 가 남아야 합니다.
- **결과:** 예를 들어 부가세 신고 절차는 이렇게 저장됩니다.

  | 항목 | 내용 |
  |---|---|
  | 언제 시작하나 | 분기 끝나고 25일 이내 |
  | 무엇이 필요한가 | 이카운트 매출·매입 자료, 위하고 원장 |
  | 어떤 순서로 | 자료 추출 → 원장 대사 → 이상 확인 → 세무대리인 확인 → 신고 |
  | **판단 기준** | "차이가 10만원 넘으면 원인 밝히기 전엔 진행 금지" |
  | 무엇이 나오나 | 신고서, 대사표, 증빙철 |

  이 중 **「판단 기준」이 AI에게 가장 중요합니다.** 순서만 있으면 따라는 하는데 *언제 멈춰야 하는지*를 모릅니다.

### 3. 반복업무를 「절차」에 흡수 (서랍 2개 삭제)

- **무엇을:** 매일·매주 체크하는 「반복업무」를 별도 개념으로 두지 않고, *주기가 정해진 절차*로 합쳤습니다. 이걸 담으려던 저장 공간 2개가 사라졌습니다.
- **왜:** 구조가 똑같았습니다. "반복업무 + 체크 기록"과 "절차 + 실행이력"이 사실상 같은 것이었습니다.
- **결과:** **매일 체크하던 행위 자체가 학습 데이터가 됩니다.** 따로 절차 문서를 쓸 필요가 없어졌습니다.

### 4. 문서 초안 기능 (AI가 공문·신고서 초안을 씀)

- **무엇을:** 「문서 양식」과 「문서」 저장 공간을 새로 만들었습니다. 사내 공지·공문·행정 신고 서류의 초안을 AI가 만들고, 사용자가 고쳐서 확정합니다.
- **왜:** 사용자가 원한 기능 중 하나였고, 절차의 결과물이 대부분 문서이기 때문입니다.
- **결과:** 쓸수록 좋아지는 구조가 됐습니다.

  ```
  문서 양식 (한 번 등록)  ┐
  확정된 과거 문서들      ├→ AI → 초안 → 내가 수정 → 확정
  이번 회차의 입력 자료   ┘                            │
          ▲                                            │
          └──── 확정된 문서가 다음 초안의 참고자료가 됨 ────┘
  ```

  **공문을 열 번 쓰면 열한 번째 초안이 눈에 띄게 좋아집니다.** 문서 자체가 학습 데이터이기 때문입니다.

### 5. 공개 정책 — 내 업무가 새어 나가지 않게

- **무엇을:** AI가 대표의 질문에 답할 때 **근거로 인용해도 되는 데이터와 안 되는 데이터**를 표로 정하고, 이걸 문서 주석이 아니라 **데이터 창고 안에 규칙 테이블로 넣기로** 했습니다.
- **왜:** 사용자의 업무 내역은 비공개인데 AI는 그 데이터로 학습합니다. 그러면 *"부장이 이 건에 3주 썼다"* 같은 게 답변에 간접적으로 새어 나갈 수 있습니다.
- **결과:** 인용 가능한 것은 「내가 발행한 이슈」·「대표가 준 지시」·「내가 확정한 리포트」뿐입니다. **소요시간이 새는 자리인 실행이력은 인용 금지**입니다. 규칙을 창고 안에 넣어뒀으니, 나중에 AI를 붙이는 사람이 이 문서를 안 읽어도 사고가 안 납니다.

## 😵 어려웠던 점 & 해결

문제가 있었던 일은 **상황 → 증상 → 원인 → 해결 → 남은 문제** 순서로 적습니다. 특히 **「남은 문제」를 빼먹지 않습니다** — 대부분의 수정은 다른 문제를 남기고, 그걸 안 적으면 다음 사람이 같은 자리를 또 팝니다.

### 🔵 1. 설계서와 계획서가 사라져 있었습니다

- **상황:** 세션을 시작하고 "지금까지 진행된 내용을 확인해달라"는 요청을 받아 현재 상태를 살펴봤습니다.
- **증상:** `docs` 폴더가 통째로 없어져 있었습니다. 설계서·구현계획·회고 3개 전부입니다.

  ```
   D docs/devlog/2026-08-09_v01.md          ← D = Deleted (삭제됨)
   D docs/plans/2026-08-09-stage1-...md
   D docs/specs/2026-08-09-personal-...md
  ```

  다행히 **git에는 남아 있었습니다.** git은 작업 기록을 시점별로 전부 보관하므로, 화면에서 사라져도 되살릴 수 있습니다.

- **원인:** **확정하지 못했습니다.** 두 가지 가능성이 있었습니다. ① 사용자가 의도적으로 지웠다 ② **OneDrive가 파일을 비웠다** — 오전 회고(v01)의 이슈 1에서 이미 한 번 겪은 일입니다. OneDrive는 "안 쓰는 파일"이라고 판단하면 내용을 비우고 껍데기만 남깁니다. 다만 이번엔 git 내부는 멀쩡해서 오전과 완전히 같은 증상은 아니었습니다.
- **해결:** 되살렸습니다. 판단 근거는 ① 되살리는 건 잃을 게 없고(git에 있는 걸 화면으로 다시 꺼내는 것뿐) ② 의도적 삭제였다면 다시 지우면 그만이라는 것이었습니다. **되살렸다는 사실을 사용자에게 먼저 알렸습니다.**
- **남은 문제:** ⚠️ **원인을 모르는 채로 넘어갔습니다.** OneDrive가 원인이면 또 일어납니다. 이번엔 사라진 파일이 **전부 기록된 상태**라 운이 좋았습니다. **아직 기록 안 한 작업이 있을 때 같은 일이 나면 그대로 날아갑니다.** 다음엔 파일 목록만 보지 말고 OneDrive 동기화 상태도 함께 확인해야 합니다.

### 🔴 2. 두 프로젝트가 같은 것을 두 번 만들고 있었습니다

**이날 가장 중요한 발견입니다.**

- **상황:** 사용자가 두 툴의 관계를 설명해 줬습니다 — *"업무관리툴은 AI가 작업하고 기록하는 툴이고, 실제 데이터 정리와 질문은 경영관리툴에서 해."* 경계를 설계하려면 상대편을 봐야 해서, 허락을 받고 경영관리서비스의 설계서를 읽었습니다.
- **증상:** 그 설계서의 **「업무관리 탭」** 항목이 이 프로젝트의 계획과 **정확히 겹쳤습니다.**

  | 저쪽 설계서 | 이쪽 계획 | |
  |---|---|---|
  | 업무 등록 | 업무 저장 공간 | 같음 |
  | 칸반 `할 일→진행중→검토요청→완료` | 칸반 화면 | **칸 이름까지 똑같음** |
  | 체크리스트 | 체크리스트 저장 공간 | 같음 |
  | 반복업무 | 반복업무 저장 공간 | 같음 |
  | 지연 관리 | **이미 만들어 놓은 계산 로직** | 중복 |
  | 중요도 P0/P1/P2 | **이미 만들어 놓은 계산 로직** | 중복 |

  게다가 저쪽 데이터 설계에도 「업무」·「마일스톤」·「체크항목」 저장 공간이 있었고, **전부 「없으면 안 되는 필수」 등급**이었습니다.

- **원인:** **두 프로젝트가 각자 따로 설계됐기 때문입니다.** 경영관리서비스는 "이슈를 발견해서 조치까지 추적한다"는 흐름을 완결하려고 업무 기능을 자기 안에 넣었고, 이 프로젝트는 "개인 업무 도구"로 출발해서 같은 것을 만들었습니다. **어느 쪽도 틀리지 않았습니다. 아무도 경계를 안 그었을 뿐입니다.**

  > 💥 **왜 이게 심각한가**
  > 같은 업무가 두 창고에 각각 들어가면
  > ① **매일 어긋납니다** — "칸반에서 옮겼는데 왜 저기선 안 옮겨졌지?"
  > ② **AI가 오염된 데이터를 배웁니다** ← 이게 진짜 문제입니다. 어느 쪽이 진짜인지 모르는 데이터로 학습한 AI는 신뢰할 수 없습니다. 학습이 목적인 도구에서 이건 치명적입니다.

- **해결:** 세 가지 방안을 놓고 사용자와 정했습니다.

  | 안 | 내용 | 결과 |
  |---|---|---|
  | **A** | 업무는 이쪽이 소유. 저쪽은 읽어가는 화면만 | ✅ **채택** |
  | B | 업무는 저쪽이 소유. 이쪽은 절차·이력만 | 폐기 — 지금까지 만든 게 대부분 무의미해집니다 |
  | C | 각자 갖고 나중에 맞추기 | 폐기 — 양방향으로 맞추면 **항상 어느 한쪽이 거짓**이 됩니다 |

  A로 정한 뒤 사용자가 한 겹 더 좁혔습니다.

  > "대외적으로 내가 어떤 업무들을 하는지까지 보고할 필요는 없으니, 이건 이슈로 공유해야겠다 하는 것들만 보내면 좋겠어."

  **이 한마디가 설계를 훨씬 단순하게 만들었습니다.** 저쪽이 이쪽을 *읽어가는* 게 아니라 내가 *고른 것만 밀어 넣는* 구조가 됐고, 기본값이 「비공개」가 됐습니다.

  부수적으로 저쪽 설계서의 **내부 모순**도 드러났습니다. 앞부분에 *"부서별 운영시스템은 만들지 않는다"* 고 써놓고 뒷부분에서 정확히 그걸 만들고 있었습니다. 업무 기능을 이쪽으로 옮기면 그 모순도 같이 풀립니다.

- **남은 문제:** ⚠️ **아직 합의된 게 아닙니다.** 설계서의 미확정 목록에 최우선(OQ-01)으로 올려뒀습니다. 경영관리서비스가 **지금 재정리 중이라 지금이 경계를 옮길 수 있는 유일한 기회**입니다. 저쪽 설계가 굳으면 중복이 확정됩니다. 그래서 다음 할 일이 **연동 계약서**입니다.

  더 근본적으로는, **저장소가 둘로 나뉜 구조 자체가 이런 중복을 계속 만들어냅니다.** 이번엔 운 좋게 발견했지만 막을 장치는 아직 없습니다.

### 🟠 3. 제가 정한 규칙이 틀렸습니다

- **상황:** 경계를 정리하면서 설계서에 이런 규칙을 넣었습니다 — *"**AI 서비스 자체를 만들지 않는다.** AI 호출·대화 인터페이스는 경영관리서비스 쪽이다."* 깔끔하다고 생각했습니다.
- **증상:** 사용자가 지적했습니다.

  > "이 부분은 고민이 많아.. 예로 전체 사내 공지글 작성이나, 공문작성, 반복되는 행정서류 작성 등은 AI를 넣어서 초안 작성을 하게 할거야. 그리고 SOP 추출이나 예외탐지는 AI가 진행하는거 아니었니?"

  맞는 지적이었습니다. 더 나쁜 건 **같은 문서 안에서 앞뒤가 안 맞았다는 것**입니다. 뒷부분에서는 *"회의 녹음을 AI가 요약한다"* 고 써놓고, 앞부분에서는 *"AI를 안 만든다"* 고 했습니다.

- **원인:** **"AI"를 한 덩어리로 봤습니다.** 실제로는 성격이 완전히 다른 두 가지였습니다.

  | | 경영관리서비스의 AI | **업무관리툴의 AI** |
  |---|---|---|
  | 누구를 위해 | 대표 · 임원 · 담당자 | **사용자 본인** |
  | 무엇을 | 회사 데이터에 대한 **질문 답변** | 내 업무를 돕는 **작업 도우미** |
  | 어떻게 생겼나 | 채팅창 | 화면 안의 **버튼** — 「초안 만들기」 |

  "질문 답변 창구는 저쪽"까지는 맞게 봤는데, 그걸 **"AI 전부가 저쪽"** 으로 넓혀버린 것이 잘못이었습니다.

- **해결:** 설계서에 절을 새로 만들어 두 AI를 분리하고, 규칙을 좁혔습니다.

  > ~~AI 서비스 자체를 만들지 않는다~~ → **대표·담당자용 대화형 질의응답 창구를 만들지 않는다**

  그리고 이 툴의 AI가 하는 일 4가지(문서 초안 / 절차 추출 / 예외 설명 / 회의록 요약)를 명시하고, **AI가 필요한 부분과 아닌 부분을 갈랐습니다.**

  | 하는 일 | 어떻게 | AI 필요? |
  |---|---|---|
  | 이상 **탐지** ("단계를 건너뛰었다", "3배 오래 걸렸다") | 계산 | ❌ |
  | 이상 **설명** ("왜 그랬는지" 문장 쓰기) | AI | ✅ |
  | 반복 **감지** (같은 업무가 3번 나왔다) | 계산 | ❌ |
  | 절차 **초안** (문장으로 정리) | AI | ✅ |

  계산으로 되는 것은 ① 자동 검증이 되고 ② **비용이 0원**이고 ③ **AI가 고장 나도 동작합니다.** AI는 그 위에 문장만 얹습니다.

- **남은 문제:** ⚠️ **"안 한다"는 규칙을 넓게 쓰는 습관이 있습니다.** 넓게 쓰면 문서는 깔끔해 보이는데 실제와 어긋나고, 오늘처럼 같은 문서 안에서 모순이 납니다. 이번엔 사용자가 잡아줬지만 다음에도 잡아준다는 보장이 없습니다.

  ⚠️ **AI 초안의 품질은 자동으로 검증할 수 없습니다.** 계산 결과가 맞는지는 기계가 확인해주지만, "이 공문 초안이 좋은가"는 판단할 수 없습니다. **초안과 최종본을 둘 다 저장해서 그 차이를 눈으로 보는 것** 말고는 방법이 없습니다 — 매번 같은 곳을 고치고 있다면 AI에게 주는 지시가 잘못된 겁니다.

### 🟡 4. 질문이 두 번이나 빗나갔습니다

- **상황:** 새 목적을 파악하려고 객관식 질문을 던졌습니다. ① *"AI 비서화의 도달점은 어디입니까?"*(알림만/수행 후 승인/완전 자동/판단 보조) ② *"AI에게 직접 질문하는 사람은 누구입니까?"*(나만/나+대표/자동 발행/팀 전체)
- **증상:** **둘 다 답변 대신 되물음을 받았습니다.** 사용자는 그 사이에 요구사항을 계속 덧붙였습니다 — 실시간 질의응답, 행정 신고 문서 초안, 자금 경고.
- **원인:** **제가 남의 제품 구조를 상상해서 선택지를 만들었습니다.** 사용자 머릿속에는 이미 이런 그림이 있었습니다.

  ```
  대표 → [경영관리툴] → AI 호출 → [업무관리툴에서 일하고 기록]
  ```

  그런데 저는 그 구조를 모른 채 **"이 툴 하나가 AI 비서가 된다"** 를 전제로 선택지를 짰습니다. **전제가 틀렸으니 어느 칸도 맞을 수가 없었습니다.**

- **해결:** 두 번째 되물음 뒤에 **질문을 멈췄습니다.** *"제 질문이 잘 안 맞는 것 같습니다. 어떤 점을 명확히 하고 싶으신지 말씀해 주세요."* 그때 사용자가 전체 구조를 한 문단으로 설명해 줬고, **그 뒤로는 막힘이 없었습니다.**
- **남은 문제:** ⚠️ **막혔을 때 더 정교한 질문을 만들려고 한 게 실수였습니다.** 전제가 틀렸을 땐 선택지를 아무리 다듬어도 안 맞습니다. **두 번째가 아니라 첫 번째 되물음에서 멈췄어야** 했습니다.

  💡 반대로 이번에 잘 통한 방법이 하나 있습니다 — **물어보기 전에 읽는 것.** 상대편 설계서를 읽고 나서야 제대로 된 질문을 할 수 있었고, **이슈 2의 중복도 그때 발견했습니다.**

## 🔀 갈림길에서 무엇을 왜 골랐나

오늘 큰 결정이 4개 있었습니다. 각각 **고른 것 / 버린 것 / 결정적 이유 / 치른 대가**를 적습니다.

### (1) 두 툴의 경계 → 안 A

| | |
|---|---|
| **고른 것** | 업무·절차·실행이력은 이쪽이 단독 소유. 밖으로는 **내가 고른 이슈만** 발행 |
| **버린 것** | B(저쪽이 업무 소유) / C(각자 갖고 나중에 맞추기) |
| **결정적 이유** | 이미 만든 계산 로직 4개가 **그대로 살아남고**, 저쪽 설계서의 내부 모순도 함께 풀립니다 |
| **치른 대가** | 저쪽에 "업무 기능을 들어내달라"고 **요청해야 합니다.** 아직 합의 전입니다 |

### (2) 설계서를 새 버전으로 따로 두지 않고 하나로 통합

| | |
|---|---|
| **고른 것** | 기존 설계서에서 필요한 부분을 흡수한 뒤 삭제하고, 새 문서를 **유일한 설계서**로 |
| **버린 것** | 기존 것을 v1으로 남기고 새 것을 v2로 두기 (제가 처음 제안한 방식) |
| **결정적 이유** | 사용자 요청이었고, **실제로 맞았습니다** — 설계서가 하나면 "어느 쪽이 진짜지"가 없습니다. 원본은 git에 영구 보존되므로 잃는 것도 없습니다 |
| **치른 대가** | "뭐가 바뀌었나"를 설계서에서 볼 수 없습니다. **그 역할을 이 회고가 대신합니다** |

### (3) 「절차」와 「문서」를 일정표 앞으로 당김

| | |
|---|---|
| **고른 것** | 2단계 = 절차와 실행이력, 3단계 = 문서와 AI 초안. **「오늘」 화면과 업무일지를 4단계로 미룸** |
| **버린 것** | 기존 순서 (2단계가 「하루의 흐름」이었습니다) |
| **결정적 이유** | 절차가 없으면 **6개월을 써도 남는 게 제목과 완료일뿐**입니다. 나중에 소급해서 정리하는 건 불가능합니다 |
| **치른 대가** | **제품의 얼굴(「오늘」 화면)이 늦게 나옵니다.** 매일 여는 맛이 4단계까지 없습니다 |

### (4) 예외를 사람이 안 적게 만들기

| | |
|---|---|
| **고른 것** | 툴이 감지하고 **사람은 확인만** — `[예외 맞음]` / `[정상임]` 두 버튼 |
| **버린 것** | 예외 기록 입력칸을 만들고 사람이 적게 하기 |
| **결정적 이유** | **안 적습니다.** "이번엔 뭐가 달랐는지 적으세요"라는 화면은 결국 비어 있게 됩니다 |
| **치른 대가** | 감지 기준(소요시간 2배, 표본 3회)이 **근거 없는 추정치입니다.** 헛감지만 내면 「정상임」만 누르다 끝납니다 |

> 같은 논리를 **절차**에도 적용했습니다. 절차는 사람의 추가 노동이 아니라 **부산물**로 나와야 합니다 — 아는 업무는 직접 쓰고, 모르던 업무는 **3회차에 툴이 초안을 제안**합니다.
