## 🛠 작업 상세

### 1. 데이터 창고 7개

- **무엇을:** 업무·지시사항·체크리스트·인박스·업체·변경이력, 그리고 **AI 공개 정책**을 담을 공간을 만들었습니다.
- **왜:** 설계서의 29개 중 1단계에 필요한 것만 골랐습니다. 절차·문서·AI 대화는 2·3단계에서 만듭니다. **한꺼번에 다 만들면 안 쓰는 공간이 방치됩니다.**
- **결과:** 클라우드에 올라갔고, 화면 코드에서 쓸 수 있는 타입이 자동 생성됩니다.

**여기서 정한 것 3가지**

| 정한 것 | 왜 |
|---|---|
| 값 목록을 **고정 타입이 아니라 검사 규칙**으로 | 고정 타입은 값을 추가할 때 절차가 번거롭습니다. 업무 출처는 계속 늘어납니다 — 「절차」와 「대표지시」가 이미 그랬습니다 |
| 「절차 연결」 칸을 **2단계로 미룸** | 연결할 절차 저장 공간이 아직 없어 연결선을 만들 수 없습니다 |
| 인박스 출처에 **아직 안 쓰는 값까지** 미리 | 1단계는 「직접」만 쓰지만, 나중에 검사 규칙을 다시 만들 일이 없게 |

### 2. 남의 데이터가 안 보이게 막기 (RLS)

- **무엇을:** 7개 저장 공간 전부에 "본인 것만 보인다" 규칙을 걸었습니다.
- **왜:** 이게 없으면 **브라우저에 들어가는 공개 열쇠만으로 전체 데이터를 읽을 수 있습니다.** 앱을 배포하는 순간 공개됩니다.
- **결과:** 7개 전부 규칙이 걸린 것을 직접 조회해 확인했습니다.

> 💡 **빠뜨리기 쉬운 것 하나**
> "볼 수 있는가"와 "만들 수 있는가"는 **다른 규칙**입니다. 앞만 걸면 **읽기는 막히는데 남의 이름으로 쓰는 건 통과**합니다. 둘 다 걸었습니다.

**공개 정책 표는 읽기만 허용했습니다.** 쓰기 규칙을 아예 안 만들면 앱에서 바꿀 수 없습니다. 이 표는 *"AI가 무엇을 인용해도 되는가"* 를 정하는 것이라, 실수로 「불가」를 「가능」으로 바꾸면 업무 내역이 새어 나갑니다. 바꾸려면 정식 절차를 밟아야 합니다.

### 3. 로그인 — 비밀번호 없이

- **무엇을:** 이메일을 넣으면 링크가 오고, 누르면 로그인됩니다.
- **왜:** 혼자 쓰는 도구라 비밀번호를 관리할 이유가 없습니다. **관리하지 않는 비밀번호가 가장 안전합니다.**
- **결과:** 다른 탭에서 로그아웃해도 즉시 반영됩니다.

### 4. 6탭 사이드바와 자리표시자

- **무엇을:** 탭 6개를 만들었는데, **1단계에서 내용이 들어가는 건 「업무」와 「기준」뿐**입니다. 나머지 4개는 자리표시자입니다.
- **왜:** 자리표시자를 "언젠가 만듭니다"로 두면 몇 달 뒤에 **"이거 왜 비어 있지"** 가 생깁니다.
- **결과:** 각 탭에 **몇 단계에서 무엇이 들어오는지** 목록으로 적었습니다. 「이슈로 공유」 버튼도 같은 이유로 자리만 만들고 안내 문구를 붙였습니다.

**첫 화면을 「오늘」이 아니라 「업무」로 보냅니다.** 「오늘」은 4단계에서 만들어지는데, 그전까지 첫 화면이 자리표시자면 **매일 열 이유가 없습니다.** 4단계에서 그 한 줄을 지우면 원래 설계로 돌아갑니다.

### 5. 업무 — 목록·칸반·등록

- **무엇을:** 목록 뷰와 칸반 뷰, 등록·수정 폼, 상세 화면과 체크리스트를 만들었습니다.
- **왜:** 1단계의 목표가 *"인박스에 던져두고 업무로 올려 칸반으로 굴린다"* 이기 때문입니다.
- **결과:** 카드를 끌어 옮기면 **화면이 먼저 바뀌고** 서버에 저장됩니다. 실패하면 되돌립니다.

> **왜 화면을 먼저 바꾸나**
> 카드를 옮겼는데 서버 응답을 기다리며 제자리에 멈춰 있으면 **"안 옮겨졌나?"** 하고 다시 끌게 됩니다.

**정렬과 기한 계산을 화면에서 다시 짜지 않았습니다.** 어제 만든 계산 로직을 그대로 씁니다. 화면에서 또 짜면 두 곳이 어긋나고, 서머타임 처리 같은 게 한쪽에만 들어갑니다.

**요청받은 업무는 회신 내용이 없으면 「완료」로 못 바꿉니다.** 설계서에 있던 규칙을 폼에서 막고 이유를 표시합니다.

**칸반은 4열이고 「보류」는 하단 별도 영역입니다.** 열로 두면 보류 카드가 쌓여 시야를 가립니다.

### 6. 인박스 — 마찰 없이

- **무엇을:** 한 줄 입력 + 엔터로 저장. 「업무로」를 누르면 중요도·기한·영역만 고르고 업무가 됩니다.
- **왜:** **마찰이 있으면 안 씁니다.** 분류를 먼저 요구하면 그냥 다른 데 적게 됩니다.
- **결과:** 승격 규칙은 어제 만든 계산 로직을 그대로 씁니다 — 60자가 넘으면 제목은 자르고 전문은 상세에 넣습니다.

### 7. 지시사항 진행률

- **무엇을:** 지시사항별로 소속 업무를 모아 진행률·완료 건수·마감일을 보여줍니다.
- **왜:** 대표 지시가 실제 업무로 어디까지 갔는지를 한눈에 보는 게 이 툴의 출발점이었습니다.
- **결과:** 집계도 어제 만든 계산 로직이 합니다. 화면은 그리기만 합니다.

## 😵 어려웠던 점 & 해결

### 🔴 1. 기본 데이터가 두 번 만들어졌습니다

- **상황:** 개발 서버를 띄우고 로그인이 되는지 확인한 뒤, 데이터가 잘 들어갔는지 세어봤습니다.
- **증상:** 업체가 **2건**, 지시사항이 **26건**이었습니다. 각각 1건, 13건이어야 합니다.

  ```
  2026-08-09 16:44:59.972  제우스
  2026-08-09 16:45:00.024  제우스     ← 52밀리초 뒤
  ```

  같은 사용자였습니다.

- **원인:** **개발 모드에서 화면이 두 번 켜집니다.** React가 실수를 잡아내려고 일부러 그렇게 합니다. 그런데 제 중복 방지 장치가 **화면이 꺼지면 같이 초기화되는 자리**에 있었습니다. 두 번 다 "업체가 없네"를 보고 각각 만들었습니다.
- **해결:** 중복 방지 장치를 **화면이 꺼져도 살아남는 자리**로 옮겼습니다. 그리고 만들기 직전에 **저장된 목록이 아니라 DB를 한 번 더** 세도록 했습니다. 두 겹입니다. 실패하면 장치를 풀어 다시 시도할 수 있게 했습니다.
- **남은 문제:** ⚠️ **이미 만들어진 중복 1건은 아직 남아 있습니다.** 지우는 명령이 안전장치에 막혔고, 우회하지 않고 확인을 받기로 했습니다. 업무·인박스가 0건이라 지워도 잃을 게 없습니다. → 확인 요청 목록 **C-00**

  💡 **더 근본적으로는** — 이런 종류의 실수는 앱 코드만으로 완전히 막기 어렵습니다. DB 쪽에 "같은 사용자가 같은 이름의 업체를 두 번 못 만든다"는 규칙을 거는 게 확실한데, 그러려면 중복이 먼저 지워져야 합니다. **중복을 정리한 뒤에 그 규칙을 걸 생각입니다.**

### 🟠 2. 공개 정책 표를 만들어 놓고 내용을 안 넣었습니다

- **상황:** 데이터가 잘 들어갔는지 세어보다가 발견했습니다.
- **증상:** `disclosure_policy` **0건**. 표만 있고 비어 있었습니다.
- **원인:** 계획서에는 "시드에 넣는다"고 적어뒀는데, **1단계 작업을 스키마·RLS·화면 순서로 진행하면서 시드 단계를 건너뛰었습니다.** 화면이 도는 걸 먼저 보고 싶었던 게 컸습니다.
- **해결:** 17건을 넣었습니다 — 인용 가능 2, 조건부 2, **불가 13**. 아직 만들지 않은 저장 공간(절차·문서·AI 대화)의 정책까지 미리 넣었습니다. 이름은 그냥 글자라 그 공간이 없어도 됩니다.
- **남은 문제:** 이 표가 **비어 있어도 앱은 멀쩡히 돌아갑니다.** AI가 3단계에 오기 때문입니다. 즉 **비어 있는 걸 아무도 눈치채지 못한 채 3단계에 갔을 수 있습니다.** 이번엔 우연히 세어보다 발견했습니다. 3단계에서 AI를 붙일 때 **정책 표가 비어 있으면 시작하지 못하게** 막는 장치가 필요합니다.

### 🟡 3. 화면 파일들이 서로 얽혀 커밋을 못 나눴습니다

- **상황:** 계획서대로 Task 5부터 12까지를 각각 커밋하려 했습니다.
- **증상:** 나눌 수가 없었습니다. 사이드바가 「빠른 입력」과 「오늘 한눈에」를 품고 있고, 그 둘이 업무·인박스 조회를 씁니다. **중간에서 자르면 그 커밋은 빌드가 안 됩니다.**
- **원인:** 계획서를 쓸 때 **파일 단위로만 생각하고 의존 관계를 안 봤습니다.** "사이드바"와 "업무 목록"이 별개 작업으로 보였는데 실제로는 한 덩어리였습니다.
- **해결:** 한 커밋으로 묶고 **왜 묶었는지를 커밋 메시지에 적었습니다.** 커밋마다 빌드가 통과하는 쪽을 택했습니다.
- **남은 문제:** ⚠️ 커밋 하나가 **32개 파일**이 됐습니다. 나중에 "이 코드 왜 이래?"를 추적할 때 이 커밋은 도움이 안 됩니다. 2단계 계획을 쓸 때는 **파일이 아니라 의존 관계로 작업을 나눠야** 합니다.

### 🟡 4. 로그인 명령을 제가 실행할 수 없었습니다

- **상황:** 데이터 창고를 만들려면 CLI가 로그인돼 있어야 했습니다.
- **증상:** `Cannot use automatic login flow inside non-TTY environments`
- **원인:** 제가 실행하는 명령은 **사람이 앉아 있는 화면이 아닙니다.** 브라우저를 띄우고 기다리는 방식이 동작하지 않습니다.
- **해결:** 사용자가 직접 PowerShell에서 실행했습니다. 토큰이 사용자 설정 폴더에 저장되므로 **한 번만 하면 이후 제 명령이 전부 그 토큰을 씁니다.**
- **남은 문제:** 없음. 다만 **처음에 방법을 잘못 안내했습니다.** 프롬프트 입력창에 `!`를 붙이라고 했는데, 사용자가 그걸 메시지로 보내면 실행되지 않습니다. **두 번 헛돌았습니다.** 대화형 명령은 처음부터 "별도 터미널에서 실행"으로 안내하는 게 낫습니다.

## 🔀 갈림길에서 무엇을 왜 골랐나

### (1) 기본 데이터를 SQL이 아니라 앱에서 만든다

| | |
|---|---|
| **고른 것** | 최초 진입 시 앱이 업체·지시사항을 만든다 |
| **버린 것** | 마이그레이션 SQL에 넣기 |
| **결정적 이유** | 업체·지시사항에는 **사용자 번호**가 필요한데, SQL에 특정 번호를 박으면 **다른 환경에서 안 돌아갑니다** |
| **치른 대가** | 시드 내용이 SQL이 아니라 코드에 있습니다. 그리고 **오늘의 중복 버그가 정확히 여기서 났습니다** — SQL이었으면 한 번만 돌았을 것입니다 |

> **공개 정책만은 SQL에 넣었습니다.** 사용자 번호가 없는 시스템 규칙이라 사용자마다 만들 필요가 없기 때문입니다.

### (2) 첫 화면을 「오늘」이 아니라 「업무」로

| | |
|---|---|
| **고른 것** | 1단계에서는 「업무」로 보낸다 |
| **버린 것** | 설계서대로 「오늘」을 첫 화면으로 |
| **결정적 이유** | 「오늘」은 4단계에서 만들어집니다. **첫 화면이 자리표시자면 매일 열 이유가 없습니다** |
| **치른 대가** | 설계와 한 줄 다릅니다. 그래서 **그 줄에 "4단계에서 지우면 원래대로 돌아간다"** 고 적어뒀습니다 |

### (3) 변경 이력을 DB가 아니라 앱에서 남긴다

| | |
|---|---|
| **고른 것** | 앱 코드에서 의미 있는 순간에만 남긴다 |
| **버린 것** | DB가 모든 변경을 자동으로 남기기 |
| **결정적 이유** | 자동은 **모든 변경을 남겨 노이즈가 많습니다.** "무엇이 의미 있는 변경인가"는 업무 규칙이라 앱이 알기 좋습니다 |
| **치른 대가** | **앱에서 빠뜨리면 기록이 안 남습니다.** 자동이었으면 빠뜨릴 수 없었습니다 |

### (4) 업무 순서를 사람이 직접 바꾸지 않는다

| | |
|---|---|
| **고른 것** | 정렬은 계산 규칙(지연 → 임박 → 정상, 그다음 중요도, 그다음 기한)을 따른다 |
| **버린 것** | 카드를 위아래로 끌어 순서 바꾸기 |
| **결정적 이유** | 사람이 손으로 옮긴 순서와 자동 정렬이 부딪히면 **어느 쪽이 맞는지 알 수 없습니다** |
| **치른 대가** | "이건 오늘 먼저 해야 해"를 순서로 표현할 수 없습니다. 중요도나 기한으로 표현해야 합니다. 필요해지면 나중에 켭니다 |

## 📚 오늘 배운 것

- **주제: 개발 모드는 일부러 화면을 두 번 켠다**
  한 줄 요약 — 실수를 잡아내려는 장치인데, **"한 번만 해야 하는 일"을 화면 안에 두면 두 번 일어납니다.** 오늘 업체가 2건 생긴 이유입니다.

- **주제: "한 번만"은 앱이 아니라 DB가 보장해야 한다**
  한 줄 요약 — 앱 코드의 중복 방지는 **막을 수 있는 경우만** 막습니다. DB에 규칙을 걸면 **어떤 경로로 와도** 막힙니다.

- **주제: 안 쓰는 데이터는 비어 있어도 아무도 모른다**
  한 줄 요약 — 공개 정책 표가 비어 있었는데 앱은 멀쩡했습니다. **쓰이지 않는 것은 틀려도 티가 안 납니다.** 쓰기 시작할 때 검사하는 장치가 필요합니다.

- **주제: 작업은 파일이 아니라 의존 관계로 나눈다**
  한 줄 요약 — 계획서에서 별개로 보였던 작업들이 실제로는 한 덩어리였습니다. **나누면 중간이 빌드되지 않습니다.**

- **주제: 계산 로직을 떼어둔 것이 오늘도 값을 했다**
  한 줄 요약 — 정렬·기한·집계·승격을 화면에서 다시 짜지 않았습니다. **화면은 그리기만 합니다.** 두 곳이 어긋날 일이 없습니다.

- **주제: 대화형 명령은 별도 터미널로 안내한다**
  한 줄 요약 — 브라우저를 띄우고 기다리는 명령은 제가 실행할 수 없습니다. 우회 방법을 찾다 **두 번 헛돌았습니다.**
