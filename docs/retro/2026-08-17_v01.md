# 2026-08-17 v01 — 회의록에 「양식」이 생기고, 음성이 세 갈래로 들어오게 되다

> 어제(08-16) 실시간 회의록을 만들었습니다. 오늘은 **그 회의록이 실제 업무 문서가 되도록** 다듬은 날입니다.

## 📌 오늘 한 일 (요약)

- **회의록 양식을 만들었습니다.** 사용자가 실무에서 쓰는 8칸짜리 양식을 그대로 담았습니다. 핵심은 하나 — **결정사항과 Action Item 을 나눈 것**
- **Action Item 이 인박스로 넘어갑니다.** 회의록이 기록으로 끝나지 않고 **업무가 되는 통로**가 생겼습니다
- **회의록을 만드는 길이 셋**이 되었습니다 — 실시간 받아쓰기 / 음성텍스트 가져오기 / 녹음 파일 올리기
- 회의록을 **PDF · 파일(.md) 로 내려받고, 복사**할 수 있습니다
- 며칠 붙들던 **브라우저 받아쓰기 문제의 진짜 원인**을 찾았습니다 — 제가 받아쓰기 장치를 잘못 고르고 있었습니다
- 받아쓰지 못한 음성을 **서버에 보관**해, 폰에서 녹음하고 노트북에서 이어 작업할 수 있게 했습니다
- **화면 문구를 업무 문서체로 전면 정비**했습니다. *"공짜"* · *"껍데기"* 같은 표현을 걷어냈습니다
- 실제 회의 전사본(1시간 46분)으로 **회의록 샘플을 만들어** 양식을 검증했습니다

## 🌅 오늘의 출발점

어제 만든 회의록은 **「안건」과 「결정사항」 두 칸의 줄글**이었습니다. 받아쓰기는 되는데,
그 결과물이 **업무 문서로는 쓸 수 없는 모양**이었습니다.

그러던 중 사용자가 실무에서 쓰는 양식을 가져오셨습니다. 그리고 이렇게 짚으셨습니다.

> *"결정사항과 Action Item은 반드시 분리하는 것을 추천합니다. A 시스템 도입하기로 결정은
> 결정사항이고, 견적 3개 업체 비교 / 담당자 / 8월 21일까지는 Action Item입니다."*

이 한 문장이 오늘 작업 전체의 축이 되었습니다.

그리고 회의 전사본 끝부분에 이런 대화가 있었습니다 — ***"저희 혹시 회의록 양식이 있나요?"***
이 프로젝트가 왜 시작됐는지가 거기 적혀 있었습니다.

## 🛠 작업 상세

### 1. 회의록 양식 — 결정과 실행을 가르다

- **무엇을:** 회의록을 8칸 양식으로 다시 짰습니다.

  ```
  1. 회의 기본정보    회의명 · 일시 · 장소/방식 · 참석자
  2. 회의 목적        이 회의를 왜 했나
  3. 주요 안건        논의한 주제 목록
  4. 안건별 논의      안건 | 주요 논의 | 결과
  5. 결정사항         정해진 것 | 비고
  6. Action Item      해야 할 일 | 담당자 | 완료기한 | 상태
  7. 미결 · 추가 확인
  8. 다음 회의        예정일 | 다룰 것
  ```

- **왜:** 회의 내용을 길게 적는 것보다 **「무엇을 결정했고, 누가 언제까지 무엇을 하는가」**가
  바로 보이는 것이 훨씬 쓸모 있습니다. 한 칸에 섞어 적으면 나중에 그걸 찾으려고
  회의록을 처음부터 다시 읽어야 합니다.
- **결과:** 회의록이 **읽는 문서에서 쓰는 문서**가 되었습니다.

### 2. Action Item 이 업무가 됩니다

- **무엇을:** 양식의 Action Item 옆에 체크칸을 두고, 고른 것을 **인박스로 보냅니다.**
  인박스에서 업무로 올리면 기한·중요도가 붙습니다.
- **왜:** 회의록이 아무리 잘 정리돼도 **거기서 끝나면 아무 일도 일어나지 않습니다.**
  회의에서 나온 일이 실제 업무 목록으로 넘어가는 통로가 필요했습니다.
- **결과:** 「회의 → 회의록 → 인박스 → 업무」가 이어졌습니다.
  회의에서 나온 말이 전부 업무가 되지는 않으므로 **인박스를 한 번 거치게** 했습니다.

### 3. 회의록을 만드는 길이 셋

- **무엇을:**

  | | 무엇 | 비용 | 언제 쓰나 |
  |---|---|---|---|
  | 🎙 실시간 받아쓰기 | 회의 중 브라우저가 받아씀 | 없음 | 노트북으로 회의할 때 |
  | 📝 음성텍스트 가져오기 | 휴대폰이 변환한 글을 붙여넣음 | **없음** | 휴대폰 녹음 앱을 쓸 때 |
  | 🎧 녹음 파일 올리기 | 파일을 올려 서버가 변환 | 시간 비례 | 브라우저 받아쓰기가 안 될 때 |

- **왜:** 브라우저 받아쓰기 하나에 기대는 것이 위험했습니다. 기기·브라우저마다 다르게 놀고,
  실제로 며칠을 헤맸습니다. **길이 하나뿐이면 그 길이 막히는 날 아무것도 못 합니다.**
- **결과:** 어떤 기기에서든 회의록을 만들 수 있습니다.
  특히 📝 는 **휴대폰 안에서 변환되므로 음성이 밖으로 나가지 않고 비용도 0원**입니다.

### 4. AI 에게 「어떻게 정리할지」를 가르쳤습니다

- **무엇을:** 사용자가 말로 설명한 정리 방침을 **AI 규칙에 그대로 옮겼습니다.**

  | 방침 | 규칙에 넣은 말 |
  |---|---|
  | 발언을 옮기지 말 것 | "줄여 쓰는 게 아니라 **논의 배경 → 합의·결정 → 후속 조치**가 보이게 다시 짠다" |
  | 안건 단위로 묶을 것 | "말한 순서가 아니라 **주제 단위**로 묶는다" |
  | 잡담·반복 제거 | "인사말·곁길 잡담은 담지 않는다. 같은 설명은 하나로 합친다" |
  | 확정 안 된 것 구분 | "「검토하기로」는 결정이 아니라 **미결 또는 할 일**" |
  | 임의로 채우지 말 것 | "숫자·담당자는 **또렷하게 들린 경우에만**. 흐릿하면 「확인 필요」로" |

- **왜:** *"단순 요약보다, 실제 결정·지시사항을 중심으로 정리하겠습니다"* 라는 사용자의 방식이
  **사람의 머릿속에만 있으면 매번 달라집니다.** 코드에 적어야 늘 같게 나옵니다.
- **결과:** 규칙이 곧 문서가 됐습니다. 다음 사람이 이 파일만 봐도 「어떻게 정리하는가」를 압니다.

### 5. 긴 회의는 구간으로 나눠 정리합니다

- **무엇을:** 전사문이 15,000자를 넘으면 구간으로 잘라 각각 정리한 뒤 **합칩니다.**
  합치는 규칙 — 겹친 줄은 한 번만, 「목적」은 첫 구간 것, 「다음 회의」는 마지막 구간 것.
- **왜:** 1시간 46분짜리 회의의 전사문은 4만 자가 넘습니다. 한 번에 넘기면 한도에 걸리고,
  넘어가더라도 **긴 글은 가운데가 묽어져** 앞부분 지시를 흘립니다.
- **결과:** 몇 시간짜리 회의도 정리됩니다. 화면에 「3/7 구간」이 표시돼 진행 상황이 보입니다.

### 6. 받아쓰지 못한 음성을 서버에 보관합니다

- **무엇을:** 변환에 실패한 음성을 **서버 보관함**에 두고, 나중에 회의록에서 「다시 변환」을
  누를 수 있게 했습니다. 문자가 되면 자동으로 삭제됩니다.
- **왜:** 처음에는 브라우저 안에만 뒀는데 **폰에서 녹음한 것을 노트북에서 볼 수 없었습니다.**
  회의는 폰으로 하고 정리는 앉아서 하는데 그 흐름이 막혔습니다.
- **결과:** 어느 기기에서나 이어서 작업할 수 있습니다.
  ⚠️ 대신 **회의 음성이 서버에 잠시 머뭅니다.** 본인만 열 수 있게 잠갔고, 공개 정책에는
  「학습에도 인용에도 쓰지 않음」으로 못 박았습니다.

### 7. 회의록을 밖으로 꺼낼 수 있습니다

- **무엇을:** 복사 · 파일(.md) · **PDF** 세 가지.
- **왜:** 회의록은 메일·결재·보고에 쓰입니다. 화면 안에만 있으면 반쪽입니다.
- **결과:** PDF 는 **브라우저 인쇄 창**을 씁니다. PDF 라이브러리를 넣으면 한글 글꼴을 몇 MB
  같이 담아야 해서 화면 여는 속도가 눈에 띄게 느려집니다. 브라우저에 이미 있는 기능을 쓰면
  한글도 그대로 나오고 앱 무게도 안 늘어납니다.

### 8. 화면 문구를 업무 문서체로

- **무엇을:** *"공짜"* → 「별도 비용이 없으며」, *"껍데기만"* → 「기본정보만」,
  *"소리"* → 「음성」, *"조각"* → 「구간」, *"버리기"* → 「삭제」 …
- **왜:** 사용자 지적이 정확했습니다 — **"이거 공적인 프로그램이야."**
  제가 쓴 문장이 대화체에 가까웠습니다.
- **결과:** 화면 어디를 열어도 같은 격의 말이 나옵니다.

## 😵 어려웠던 점 & 해결

### 🔴 1. 며칠 헤맨 받아쓰기 문제 — 원인은 제 코드였습니다

- **상황:** 브라우저 받아쓰기가 마이크는 열고 소리도 잡는데 **글자를 한 자도 안 내놨습니다.**
  브라우저 탓인지, 회사망 탓인지, 마이크 탓인지 며칠을 짐작했습니다.
- **증상:** 오류조차 나지 않았습니다. 10초를 듣고 조용히 끝났습니다.
- **원인:** **크롬에는 받아쓰기 장치가 두 개** 들어 있습니다.
  오래 쓰인 것(`webkitSpeechRecognition`)과 나중에 생긴 표준 이름(`SpeechRecognition`).
  제 코드는 **이름이 표준이니 그게 맞겠지** 하고 표준 쪽을 먼저 집었습니다.
  그런데 그쪽은 소리만 받고 아무것도 돌려주지 않았습니다.
- **해결:** ① **오래 검증된 쪽을 먼저** 쓰게 바꿨습니다 ② **점검 도구**를 만들어
  어느 단계에서 멈추는지 눈으로 보게 했습니다.
- **남은 문제:** 점검 도구를 **처음부터 만들었다면 10초에 끝날 일**이었습니다.
  안 보이는 것을 짐작으로 좁히려 한 것이 시간을 잡아먹었습니다.

### 🔴 2. 도와주려고 넣은 장치가 잘 되던 것을 망가뜨렸습니다

- **상황:** 받아쓰기가 되기 시작한 뒤 사용자가 알려 주셨습니다 —
  *"말을 자꾸 지워버리고, 29초쯤 되니 그냥 멈춰버리네."*
- **증상:** 글자가 떴다가 사라지고, 30초쯤에 받아쓰기가 죽었습니다.
- **원인:** **제가 넣은 자동 전환 때문이었습니다.** 안 될 때를 대비해
  15초에 방식을 바꾸고 30초에 장치를 바꾸게 해 뒀는데 —
  · 바꿀 때마다 판이 끊기고, 끊기면 **확정 전 글자가 통째로 사라집니다**
  · 30초에 갈아탄 곳이 하필 **글자를 안 돌려주는 그 장치**였습니다
- **해결:** ① 판이 끝날 때 **듣던 말을 굳혀서 담게** 했습니다 ② **자동 전환을 전부 걷어냈습니다.**
  바꾸는 것은 사람이 버튼으로 합니다.
- **남은 문제:** 「안 될 때를 대비한 장치」가 **정상일 때를 망가뜨리지 않는지**를
  같이 생각해야 합니다. 이번엔 그걸 놓쳤습니다.

### 🔴 3. 파일을 잘못 잘라 코드 절반이 날아갔습니다

- **상황:** 화면 배치를 바꾸려고 파일을 「로직 부분」과 「화면 부분」으로 나눠 붙이려 했습니다.
- **증상:** 붙이고 나니 **저장·변환 기능이 통째로 사라져** 있었습니다.
- **원인:** 「`  return (`」라는 글자를 찾아 자르게 했는데, 그 글자가 **파일 위쪽 다른 곳에도**
  있었습니다. 엉뚱한 자리에서 잘린 것입니다.
- **해결:** 날아간 부분을 다시 쓰고, 이후로는 **더 긴 문장으로** 자를 자리를 찍었습니다.
- **남은 문제:** ⚠️ 급히 복구한 코드라 **녹음 파일 올리기는 실제로 한 번 돌려봐야** 합니다.
  빌드와 테스트는 통과했지만 그건 「말이 된다」이지 「동작한다」가 아닙니다.

### 🟡 4. 같은 화면이 파일 안에 네 번 들어 있었습니다

- **상황:** 회의록 상세 화면을 여러 번 고치다 보니 파일이 1,065줄이 됐습니다.
- **증상:** 같은 구간이 **네 벌** 들어 있었습니다. 그런데도 빌드는 통과했습니다.
- **원인:** 부분 교체를 반복하면서 **앞의 교체가 남긴 조각 위에 또 얹었기** 때문입니다.
- **해결:** **통째로 다시 썼습니다.** 500줄로 줄었습니다.
- **남은 문제:** 화면 코드를 여러 번 부분 수정할 바에는 **한 번 다시 쓰는 편이 빠릅니다.**

### 🟡 5. 음성이 서버에 한 개도 안 올라갔습니다

- **상황:** 음성 보관 기능을 만들고 저장했는데 **목록이 계속 0개**였습니다.
- **증상:** 회의록은 정상 저장되고 음성만 조용히 사라졌습니다.
- **원인:** 브라우저가 만드는 형식 이름이 `audio/webm;codecs=opus` 인데, 보관함은
  허용 목록(`audio/webm`)과 **글자 그대로** 맞춰 봅니다. 세미콜론 뒤가 붙어 있어
  「허용되지 않은 형식」으로 거절당했습니다.
- **해결:** 뒤에 붙은 부속 설명을 떼고 올립니다.
- **남은 문제:** 더 나빴던 건 **실패가 눈에 안 띄었다**는 점입니다. 화면 구석에만 떴습니다.

### 🟡 6. 탭마다 화면 폭이 달랐습니다

- **상황:** 사용자가 *"섹션별 크기가 달라"* 라고 알려 주셨습니다.
- **증상:** 탭을 옮길 때마다 화면이 좁아졌다 넓어졌다 했습니다.
- **원인:** 두 탭이 카드 한 장짜리였을 때 **720px 로 좁혀 둔 껍데기**가,
  2단 배치로 바꾼 뒤에도 남아 있었습니다.
- **해결:** 껍데기를 걷어냈습니다.
- **남은 문제:** **구조를 바꿀 때 예전 제약이 남아 있는지** 확인하는 습관이 필요합니다.

### 🟡 7. 버튼을 잠갔더니 「고장」으로 보였습니다

- **상황:** 사용자가 *"회의록 등록이 안 돼서 확인은 못 했는데"* 라고 하셨습니다.
- **증상:** 눌러도 아무 일이 없었습니다.
- **원인:** 회의명이 비면 저장 버튼을 **비활성**으로 뒀습니다. 그러면 눌러도 반응이 없어
  **왜 안 되는지 알 수가 없습니다.**
- **해결:** 버튼은 항상 눌리게 두고, 누르면 **왜 안 되는지 말해 주고 그 칸으로 데려갑니다.**
- **남은 문제:** 없음. 다만 「막는 것」과 「알려 주는 것」은 다르다는 것을 다시 배웠습니다.

## 🔀 갈림길에서 무엇을 왜 골랐나

### 회의록 분류를 몇 개로 할까

| | |
|---|---|
| **고른 것** | **6개로 통합** + 「결정 / 실행 / 미결」 상태 축을 따로 |
| 버린 것 | 사용자가 제시한 기능별 10개 그대로 |
| **결정적 이유** | 실제 회의 하나를 넣어 보니 **빈 칸이 생기고 한 건이 두세 곳에 걸쳤습니다.** 「아파트 임대료」는 세무이면서 법무입니다. 그리고 분류보다 **「결정됐나 · 실행 중인가 · 미결인가」**가 훨씬 자주 찾는 정보였습니다 |
| **치른 대가** | 기능 구분이 거칠어집니다. 회계와 세무를 따로 보고 싶을 때는 아쉽습니다 |

### PDF 를 어떻게 만들까

| | |
|---|---|
| **고른 것** | **브라우저 인쇄 창** (사용자가 「PDF로 저장」 선택) |
| 버린 것 | PDF 만드는 라이브러리 넣기 |
| **결정적 이유** | 라이브러리를 넣으면 **한글 글꼴을 몇 MB 같이 담아야** 합니다. 회의록 한 장 뽑자고 앱 전체가 느려집니다 |
| **치른 대가** | 「저장」이 아니라 「인쇄 → PDF 선택」이라 한 걸음 더 갑니다 |

### 음성을 서버에 둘까

| | |
|---|---|
| **고른 것** | **둔다** (사용자 판단) |
| 버린 것 | 브라우저 안에만 두기 |
| **결정적 이유** | 브라우저 안에만 두면 **폰에서 녹음한 것을 노트북에서 못 봅니다.** 크롬 계정 동기화는 사이트 데이터를 옮기지 않습니다 |
| **치른 대가** | **회의 음성이 서버에 잠시 머뭅니다.** 문자가 되면 지우고, 본인만 열 수 있게 잠갔지만, 소리는 글보다 사적입니다 |

### 자동으로 도와줄까, 사람이 고르게 할까

**사람이 고르게** 했습니다. 툴이 알아서 방식을 바꾸던 장치가 **잘 되던 판을 끊었습니다.**
이제 12초 넘게 글자가 없으면 **버튼만 보여 드리고**, 누를지는 사람이 정합니다.
