## 🛠 작업 상세

### 1. 화면을 만들 기본 틀 설치

- **무엇을:** React(화면 만드는 도구) + Vite(개발 서버) + TypeScript(오타·타입 실수를 미리 잡아주는 언어) + Tailwind(스타일 도구) 조합으로 프로젝트를 새로 만들었습니다.
- **왜:** Streamlit으로는 위에 적은 세 가지 문제를 풀 수 없었습니다.
- **결과:** 개발 서버가 뜨고, 빌드(실제 배포용 파일 만들기)가 통과합니다.

### 2. 애플 스타일 디자인 규격 등록

- **무엇을:** 색·글자 크기·모서리 둥글기 같은 것을 **한 곳에 정의**해두고 화면 어디서든 불러 쓰게 했습니다.
- **왜:** 화면마다 색을 따로 적으면 나중에 색 하나 바꾸는 데 파일 수십 개를 고쳐야 합니다.
- **결과:** 파란색(`#0066cc`)·본문 17px·둥근 버튼 같은 규격이 한 파일에 모였습니다.

### 3. 계산 로직 4개 (자동 검사 35개)

- **무엇을:** 화면이나 데이터 창고와 무관하게 **계산만 하는 부분** 4개를 만들었습니다.

  | 무엇을 계산하나 | 예 |
  |---|---|
  | 기한까지 며칠 남았나 | "D-3", "오늘 마감", "2일 지연" |
  | 업무를 어떤 순서로 보여줄까 | 지연 → 임박 → 정상, 그다음 중요도, 그다음 기한 |
  | 지시사항별 진행률 합산 | 소속 업무 5개의 평균 진행률과 완료 건수 |
  | 메모를 업무로 바꾸는 규칙 | 60자 넘으면 제목은 자르고 전문은 상세에 보관 |

- **왜:** 설계 단계에서 **"날짜 경계 계산이 틀리기 쉽다"** 고 짚어뒀습니다. 이 계산이 데이터 창고에 붙어 있으면 검사가 느리고 불안정해집니다.
- **결과:** 자동 검사 35개가 **1.7초**에 돕니다. 그리고 실제로 이 구조 덕분에 아래 이슈 3의 결함을 잡았습니다.

## 😵 어려웠던 점 & 해결

### 🔴 1. 작업 기록 보관소가 통째로 망가져 있었습니다

- **상황:** 프로젝트 폴더에서 작업 기록(git) 상태를 확인하려 했습니다.
- **증상:** `.git`(작업 기록이 담긴 폴더)이 분명히 있는데, 상태를 물어보면 **"여기는 git 저장소가 아닙니다"** 라는 답이 나왔습니다.
- **원인:** `.git` 폴더가 **OneDrive의 「클라우드 자리표시자」로만 남아 있었습니다.** 폴더 이름은 있는데 **안이 텅 비어 있는 상태**입니다. OneDrive는 "안 쓰는 파일은 클라우드에만 두고 내 컴퓨터에서는 지우는" 동작을 하는데, 그게 작업 기록 파일에까지 적용된 것입니다. 폴더 속성을 확인해보니 "실제 파일이 아니라 링크"라는 표시가 붙어 있었습니다.
- **해결:** 안에 아무것도 없어서 **잃을 게 없었습니다.** 지우고 새로 만들었습니다.
- **남은 문제:** ⚠️ **OneDrive 폴더 안에서 작업 기록을 관리하면 이런 일이 또 생깁니다.** 근본 해결책은 저장소를 OneDrive 밖으로 옮기는 것입니다. 지금은 그대로 두되, **기록이 이상하면 이것부터 의심**해야 합니다.

### 🔴 2. 사외 반출 금지 문서가 외부 서버에 올라갈 뻔했습니다

- **상황:** 처음엔 상위 폴더 전체를 저장소로 잡으려 했습니다.
- **증상:** 그 폴더 안에 **「내부 자료 · 사외 반출 금지」** 라고 표지에 명시된 사업이해자료가 들어 있었습니다.
- **원인:** GitHub는 비공개로 설정해도 **외부 서버**입니다. 「올리지 말 것」 목록(`.gitignore`)으로 막을 수도 있지만, **규칙 한 줄만 실수해도 그대로 올라갑니다.**
- **해결:** 저장소 범위를 한 단계 아래 폴더로 내렸습니다. 그러면 사업이해자료·PRD·데이터베이스 파일이 **애초에 관할 밖**이라 실수의 여지 자체가 없어집니다. 첫 기록 전에 실제로 어떤 파일이 포함됐는지 목록으로 확인도 했습니다.

  > 💡 **왜 이 방법인가**
  > `.gitignore`는 **"올리지 말라고 부탁하는 것"** 이고, 저장소 밖에 두는 건 **"올릴 수가 없는 것"** 입니다.
  > **되돌릴 수 없는 사고에는 후자를 씁니다.**

- **남은 문제:** 없음. 구조적으로 막았습니다.

### 🟠 3. 검사가 시간대에 따라 깨지는 상태였습니다 — 가장 중요한 이슈

- **상황:** 기한 계산 로직을 만들고 자동 검사를 돌렸습니다.
- **증상:** **당장은 아무 문제가 없었습니다.** 검사 16개가 전부 통과했습니다. 문제는 검사의 기준 시각이 이렇게 돼 있었다는 것입니다.

  > 기준 시각을 **"2026년 8월 11일 오전 9시(한국 시간)"** 이라고 못 박아뒀습니다.

- **원인:** 이 표기는 **지구 전체에서 같은 한 순간**을 가리킵니다. 그런데 실제 계산은 **"내 시계로 오늘이 며칠인가"** 를 봅니다. 이 둘은 한국·독일처럼 시계가 앞선 지역에서만 일치합니다.

  뉴욕에서 돌리면 같은 순간이 **8월 10일**이 됩니다. "오늘"이 하루 밀리면서 검사 4개가 한꺼번에 깨집니다.

  > 즉 **출장을 가거나 노트북 시간대가 다르게 잡혀 있으면 빨간 화면을 보게 됩니다.**

  **하마터면 놓칠 뻔한 부분이 있습니다.** 처음엔 "뉴욕 시간대로 돌려보기" 명령으로 확인했고 **"통과했다"는 결과**가 나왔습니다. 그런데 **그 결과가 거짓이었습니다.** 윈도우에서는 그 명령이 무시되고, 실제로는 계속 한국 시간으로 돌아가고 있었습니다. 실제 시간대를 직접 찍어보니 세 번 다 서울이었습니다. **검증 방법 자체를 검증하지 않았으면 "문제 없음"으로 결론 낼 뻔했습니다.**

- **해결:** 계산 로직은 그대로 두고 **검사의 기준 시각만** 바꿨습니다.

  > "2026년 8월 11일 오전 9시" — **어느 시간대에서 돌리든 그 지역의 8월 11일 오전 9시**를 뜻하는 방식으로.

  이제 **운이 좋아서 통과하는 게 아니라 구조적으로 통과합니다.**

  **왜 계산이 아니라 검사를 고쳤나** — "내 시계 기준으로 오늘"이라는 게 이 업무의 규칙이 맞기 때문입니다. 사용자가 보는 "오늘"은 세계 표준시가 아니라 **자기 시계**입니다. 계산이 옳고 검사가 틀렸습니다.

- **남은 문제:** **같은 문제가 계획서의 다른 작업에도 있어서 미리 고쳤습니다.** 안 고쳤으면 정렬 검사가 같은 결함을 그대로 물려받았을 것입니다. 그리고 **윈도우에서는 시간대를 바꿔 검사할 방법이 없다는 것**이 그대로 남습니다.

### 🟡 4. 구현 계획서 자체에 오류가 있었습니다

- **상황:** 계획서에 적힌 검사 개수와 실제 개수를 대조했습니다.
- **증상:** 계획서에는 15개라고 적혀 있는데 **실제로는 16개**였습니다.
- **원인:** 계획을 쓸 때 손으로 센 것이 틀렸습니다. 5 + 7 + 4 = 16인데 15로 적었습니다.
- **해결:** 16 / 22 / 28 / 35로 바로잡고 기록했습니다(`9c6e847`).

  **파장이 있었습니다.** 뒤따르는 작업이 전부 누적 개수를 쓰기 때문에 21 / 27 / 34가 **전부 하나씩 밀려 있었습니다.** 그대로 뒀으면 *"22개 나왔는데 계획서는 21개라니, 뭔가 잘못됐나?"* 하고 헛수고할 뻔했습니다.

- **남은 문제:** **계획서의 숫자도 검증 대상입니다.** 실제 실행 결과와 다르면 계획서를 고칩니다.

### 🟡 5. 설치된 도구 버전이 예상보다 훨씬 최신이었습니다

- **상황:** 프로젝트를 새로 만들면서 도구들이 자동으로 설치됐습니다.
- **증상:** 설치된 것들이 계획을 쓸 때 상정한 것보다 **한 세대 앞선 버전**이었습니다 — Vite 8.2, TypeScript 6.0, React 19.2, 검사 도구 4.1, Tailwind 4.3.
- **원인:** "최신 버전으로 설치" 명령을 썼는데, 그 사이 새 버전이 나와 있었습니다.
- **해결:** 빌드와 검사가 전부 통과하는 것을 확인하고 **그대로 갔습니다.**
- **남은 문제:** ⚠️ 버전이 다르면 사용법도 달라집니다. 특히 Tailwind는 3과 4의 설정 방식이 **완전히 다릅니다**(4에는 설정 파일이 아예 없습니다). 그래서 **앞으로 뭔가 이상하면 버전 차이를 먼저 의심**하도록 작업 규칙에 적어뒀습니다.

### 🟡 6. 검사 파일에서 명령어를 못 알아보는 문제

- **상황:** 계산 로직 검사 파일을 만들고 빌드했습니다.
- **증상:** 검사에 쓰는 기본 명령어들을 **"모르는 이름"이라며 오류**를 냈습니다.
- **원인:** 프로젝트를 만들 때 자동 생성된 설정이, 검사 도구가 쓰는 명령어 목록을 **포함하지 않은 채 고정**돼 있었습니다.
- **해결:** 설정에 검사 도구 항목을 추가했습니다.
- **남은 문제:** 없음. 다만 **이걸 안 했으면 계산 로직 4개의 검사 파일이 전부 빌드를 깨뜨렸을** 것입니다.

### 🟡 7. 명령 문법을 잘못 써서 기록 메시지가 깨졌습니다 (두 번)

- **상황:** 여러 줄짜리 기록 메시지를 작성했습니다.
- **증상:** 메시지에 `@` 문자가 그대로 남았습니다.
- **원인:** 윈도우 환경이라 무심코 **윈도우용 문법**을 썼는데, 실제로 쓰던 건 **다른 문법 체계**였습니다. 그쪽에서는 `@`를 특별 취급하지 않아 글자 그대로 들어갑니다.
- **해결:** 둘 다 기록을 고쳐 썼습니다. 외부에 올리기 전이라 영향은 없었습니다.
- **남은 문제:** ⚠️ **두 번 났습니다.** 그래서 작업 규칙에 "이 문법을 쓰지 말고 저 문법을 쓸 것"으로 못 박았습니다.

| **버린 것** | Streamlit(v1~v3까지 만든 것) → React + 내 PC 서버 |
| **결정적 이유** | **"PC가 꺼져 있을 때도 써야 하는가"** 였습니다. 내 PC가 서버면 PC가 꺼질 때 서비스도 꺼집니다. 노트북·폰에서 항상 쓰려면 클라우드가 필요합니다 |
| **치른 대가** | 업무 데이터가 **외부 서버에 저장됩니다.** 회사가 이미 이카운트·위하고 같은 외부 서비스를 쓰고 있어서 그 자체가 금기는 아니지만, **회생·인사 회의는 결이 다릅니다.** 그래서 민감 회의는 전사문을 클라우드에 저장하지 않고 내 PC에만 두기로 했습니다 (설계서 §4.3) |

### (2) 음성 인식을 내 PC에서 돌립니다

| | |
|---|---|
| **고른 것** | 내 PC의 그래픽카드로 음성 인식 |
| **버린 것** | 클라우드 음성 인식 서비스 |
| **결정적 이유** | 음성을 클라우드로 보내면 **회의 내용이 통째로 외부에 나갑니다.** PC 사양을 확인해보니 그래픽카드(RTX 3060 6GB)가 충분했고, 1시간 회의가 **2~5분**이면 처리됩니다. 클라우드를 쓸 이유였던 속도 이점이 거의 사라졌습니다 |
| **치른 대가** | PC가 꺼져 있으면 **처리가 밀립니다.** 켜면 밀린 것부터 처리합니다 |

### (3) 계산 로직을 데이터 창고에서 분리했습니다

| | |
|---|---|
| **고른 것** | 계산만 하는 부분을 별도 폴더로 분리 (데이터 창고도 화면도 안 씀) |
| **버린 것** | 계산을 데이터 창고 조회와 섞어 짜기 |
| **결정적 이유** | 설계 단계에서 **"날짜 경계 계산이 틀리기 쉽다"** 고 짚었는데, 창고에 붙어 있으면 검사가 **느리고 불안정**해집니다 |
| **치른 대가** | 없다시피 합니다. 검사 35개가 **1.7초**에 돌고, **실제로 이 구조 덕분에 이슈 3의 결함을 잡았습니다** |

### (4) 인박스를 1단계로 앞당겼습니다

| | |
|---|---|
| **고른 것** | 인박스(분류 전 메모를 던져두는 곳)를 1단계에 포함 |
| **버린 것** | 원래 계획대로 2단계에 두기 |
| **결정적 이유** | **하루 종일 쓰는 진입점**이라 「오늘」 화면보다 먼저 있어야 쓸모가 있습니다 |
| **치른 대가** | 1단계 인박스는 **직접 던져둔 메모만** 받습니다. 회의록·전화메모에서 흘러드는 경로는 3·4단계에서 붙습니다 |

## 📋 남은 것과 다음

데이터 창고 접속 정보를 받았으므로, 막혀 있던 14개 작업을 이어갑니다.

| 순서 | 할 일 | 왜 필요한가 |
|---|---|---|
| 1 | 데이터 저장 구조 만들기 (저장 공간 6개) | 업무·지시사항·체크리스트·인박스 등을 담을 곳 |
| 2 | **보안 장치(RLS) 적용** | **이게 없으면 공개 열쇠만으로 전체 데이터가 뚫립니다** |
| 3 | 데이터 창고 연결 + 타입 자동 생성 | 창고 구조와 코드가 어긋나는 걸 미리 잡아줍니다 |
| 4 | 로그인, 사이드바 5탭, 업체 전환 | |
| 5 | 업무 목록·등록·칸반, 초기 데이터, 지시사항 | |
| 6 | 인박스 입력·승격, 빠른 입력 | |
| 7 | 전체 점검, 옛 Streamlit 앱(v1~v3) 제거, 설명서 | |

### ⚠️ 확인이 필요한 것

- **데이터 창고 지역이 싱가포르로 잡혔습니다.** 서울이 아닙니다. 쓰는 데 문제는 없고 응답이 조금 느린 정도입니다. 나중에 옮기려면 **프로젝트를 새로 만들어 처음부터 다시 올려야** 합니다.
- **로그인 관련 주소 설정**이 되어 있어야 이메일 링크 로그인이 동작합니다. 해당 작업에서 확인합니다.
